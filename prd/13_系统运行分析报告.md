## 6. 重点问题根因分析

### 6.1 P0-1：DeepSeek 密钥被拒，AI 摘要功能全废（21 次）—— ✅ 已恢复

**现象**：10/8 09:25 起，每个交易日 11:32/15:01 两个定时任务准时失败：

**现象**：10/8 09:25 起，每个交易日 11:32/15:01 两个定时任务准时失败：
```
WARNING ai_summary:_generate_ensemble:188 - ⚠️ DeepSeek V4调用失败: HTTP...
ERROR   ai_summary:_generate_ensemble:191 - 所有模型调用失败，降级到本地规则
"error": { "message": "Invalid API Key", "param": "Please provide valid API Key..." }
```

**排查过程与根因**（2026-10-17 修正定性）：
1. 服务器与本地 `.env` 密钥指纹比对**完全一致**（`DEEPSEEK_API_KEY=sk-fc6f7617f…`、`MIMO_API_KEY=tp-ca2ly3byx…`）——**排除配置漂移**，服务器没有用错密钥
2. DeepSeek 服务端返回 401 `Invalid API Key`——初步判定为"密钥本身已被拒绝"（过期/被删/额度问题）
3. **10-17 定性修正**：用户确认 DeepSeek 账户当时**欠费停机**，充值后**原密钥直接恢复可用**——实测 `POST https://api.deepseek.com/v1/chat/completions` 返回 **HTTP 200**（"Pong!"）。即：密钥从未失效，401 是欠费停机的表现形式。**处置动作从"轮换密钥"降级为"充值恢复 + 余额监控"**
4. 次要隐患：本地 `.env` 的 `OPENAI_BASE_URL=https://api.deepseek.com/v1` 已带 `/v1`（正确）；**服务器端 `.env` 此前读取记录为缺 `/v1`，待凭据文件读取审批通过后复核修正**

**影响面**：早盘/全日 AI 总结内容退化为本地规则模板；信号评级、扫描、推送等其他功能不受影响（双模型 ensemble 之外的链路不依赖 AI）。**停摆期 10/8–10/16 共 9 天、21 次失败**。

**处置（10-17 更新）**：
1. ✅ **已完成**：账户充值 → 原密钥恢复 → 实测 200。**不轮换密钥**（轮换反而引入两端不同步风险）
2. ⬜ **待办**：复核服务器 `.env` 的 `OPENAI_BASE_URL` 是否带 `/v1`（凭据文件读取待审批）
3. ⬜ **待办**：给 ai_summary 加"连续失败 N 次发钉钉告警"（目前失败只落日志，人只能主动查才发现——本次 21 次失败就是这样拖了 9 天才发现）；同时建议在 DeepSeek 控制台设置**余额不足提醒**，避免再次因欠费静默停摆

### 6.2 P0-2：worker 内存泄漏，反复 OOM（全史 8 次 + 今日第 9 次前奏）

**现象**：今日 17:36:15 `quant-worker.service: Failed with result 'oom-kill'`（Main process exited, code=killed, status=9/KILL），systemd 自动重启恢复（NRestarts=1）。历史同类事件：7/8、7/17、8/21、9/6、9/10、9/16、9/18 共 7 次（其中 7/8 连带 api OOM 一次）。

**数据画像**：

| 时间 | 事件 | systemd 记录的内存峰值 |
|---|---|---|
| 9/16 06:41 | worker OOM | 582.6M |
| 9/18 16:01 | worker OOM | 688.9M |
| 9/23 06:22 | worker 消耗记录 | 433.4M |
| 9/26 06:16 | worker 消耗记录 | 507.8M |
| 10/16 17:36 | worker OOM（今日） | 572.6M |

**根因分析**：
- **机器总内存仅 1,607MB**（当前 used 1057 / available 550），worker 峰值 572-689MB 已占 36-43%，叠加 api/beat/Redis/guardian 后触顶
- 峰值多在**早盘 6-7 点数据加载时段**与**长时间运行后**出现，符合"运行越久内存越高"的泄漏特征（9/16 进程运行 5 天 23 小时后 582.6M）
- `MemoryMax=infinity`——systemd 未对 worker 设内存上限，无法在泄漏初期自动重启止损，全靠内核 OOM killer 随机挑选受害者（可能误杀 api/Redis，风险更大）
- 泄漏候选：行情数据缓存（data/cache）、pandas DataFrame 长生命周期持有、Celery 任务结果堆积——需在代码层用 memory_profiler/tracemalloc 定位

**处置**：① 立即给三个服务设 `MemoryMax`（worker 建议 600M、api 400M、beat 400M），把生杀大权从内核 OOM killer 收回 systemd；② 代码层定位泄漏对象；③ 中期换 2G+ 内存机器或把数据加载改为流式。

### 6.3 P1-1：/api/evaluation/runs 持续 500（schema 演进不兼容）

**现象**：HTTP 500 + api 日志 pydantic 报错，至少出现在 10/3、10/9、10/14、10/15、10/16 五个日期：
```
routes.py:722  return [PostEvalResponse(**r) for r in runs]
ValidationError: 5 validation errors for PostEvalResponse
  win_count / win_rate / avg_pnl / avg_max_profit / avg_max_drawdown — Field required
```
**根因**：Redis 里的旧 run 记录（run_20260903 等）缺 5 个评估字段，而 `PostEvalResponse` 模型新增了这些必填字段——**读旧数据撞上新 schema**。属典型的数据-模型版本不兼容。
**处置**：① 短期给 PostEvalResponse 的 5 个字段设默认值（兼容读取）；② 中期写迁移脚本回填 Redis 旧 run 记录；③ 长期所有 Redis 读写模型加 `model_config = ConfigDict(extra='ignore')` 式的前向兼容。

### 6.4 P1-2：市场宽度数据异常（100% 上涨 / 均涨幅 11.35%）

**现象**：
- `/api/market`：total:100、up:100、avg_change:**11.35**（全市场股票全涨且均涨 11%+，不可能）
- 系统自校验 `/api/validation` 已报警："平均涨跌幅异常: 11.25"（success_rate 0%）
- 10/14 09:41/09:46/09:56 推送警报三次"普涨行情：上涨比例100%"——**比例超过 100% 的文案 bug 症状**

**代码路径**（market_analyzer.py `_calculate_breadth`）：`get_stock_list()` → `get_realtime_quote(codes)` → `up = len(quotes[change_pct > 0]); return up/total`。**计算逻辑本身正确**，异常来自输入：东财冷却期间实时行情返回了脏数据（change_pct 字段口径错误或缓存了旧快照），100 只股票全部 >0。
**处置**：① 在 `get_realtime_quote` 出口加数据卫生断言（change_pct 落在 [-11%, 11%]、up/total 夹紧到 [0,1]）；② 宽度异常时禁止触发"普涨行情"类警报（加阈值确认）；③ 警报文案用 `min(ratio,1.0)` 夹紧。

### 6.5 P1-3：guardian 旧服务 37 万次空转崩溃循环

**现象**：`guardian.service`（v2 旧守护进程）自 6/8 起 `activating (auto-restart)`，NRestarts=**370,749**，每 30s 一次。单元文件显示 `ExecStart=/stock_monitor/.venv/bin/python /stock_monitor/guardian.py --daemon`——**.venv 已在早期清理中被删**，每次启动必然 203/EXEC。
**影响**：全天候每 30s 一次 fork/exec 失败，烧 CPU、刷 journald（journal 2.7GB 它贡献巨大）、干扰运维视线（`systemctl --failed` 永不干净）。
**处置**：`systemctl disable --now guardian && systemctl mask guardian`（v2 服务已被 v5.0 三服务完全取代，无保留价值）。
