## 1. 核心纪律：当日可知（无未来函数）

**定义**（调研线口径）：T 日收盘后生成信号，只允许使用 T 日及之前的数据；成交发生在 T+1 开盘。

| 环节 | 纪律 | 违反后果 |
|---|---|---|
| 信号生成 | T 日收盘数据算信号 | 用 T 日盘中/未来数据 = 自欺 |
| 成交 | T+1 开盘价（跳空按实际开盘价） | 按信号价成交 = 高估收益 |
| 止损触发 | T+N 日开盘已跌破则按开盘价成交（悲观口径） | 按止损价成交 = 低估亏损 |
| 指标 | MA/RSI/KDJ/筹码全部由日K自算，截至 T 日 | 用 T+1 发布的指标 = 未来函数 |
| 基本面 | PR 为 point-in-time：中报发布前用 FY2025 年报，8 月底发布后切换滚动 TTM（FY25+H1_26−H1_25） | 用当期已发布财报反推历史 = 未来函数 |

**双轨差异说明（如实记录）**：产品实现线为**盘中实时扫描**（9:30-11:30 / 13:00-15:00，5 分钟轮询 + WebSocket 推送），信号在盘中产生并即时推送；调研方法论线的验证口径为日级批处理（收盘后计算、T+1 开盘成交）。两条口径的差异是设计取向不同（产品重实时发现、调研重可验证统计），**回测结论（06）只对调研口径成立，不可直接外推为产品盘中信号的收益承诺**。

**踩坑记录**：tech 指标按动作日逐个拉取导致 899 天中仅 112 天覆盖，RSI6 过滤误杀 51 个动量信号 → 改为日K自算。

## 4. 仓位约束（Kelly 体系，双轨并列）

### 4.1 调研线（rules v1.5，写入纪律）

```
f* = (bp − q) / b          # 凯利公式，p=胜率 q=1−p b=盈亏比
f_half = f* × 0.5          # 半凯利（防参数高估）
f_adj = f_half × √(N标的/N信号)   # 相关性折扣（同源信号不重复下注）
f_final = min(f_adj, 25%)  # 单规则仓位上限
负期望（f*≤0）→ 仓位 = 0    # 自动禁用
```

- 相关性折扣必须**分池计算**（主池/扩展池不可混算）
- 单位铁律：`position_pct` 全链路**百分数**（15.0=15%），入库前断言 `0 < position ≤ 25`
- **当前执行参数（v1.5 = 3M 口径）**：R02 9.15% / R01 2.46% / R04 2.92% / R05 2.66% / 混合 3.70%；"双窗口取保守者"原则，参数表与推导见 06 §3.1 与 14 §5.6
- **R06 倒T 已为负期望规则**（两窗口均亏）→ v1.5 起 direction=avoidance，**不再占用 Kelly 仓位**（05 §4）

### 4.2 产品线（PositionSizer，代码实证）

八步计算：动态参数读取（SignalTracker ≥10 笔）→ 基础仓位（评分 90+→40% / 80-90→35% / 70-80→30% / 60-70→25% / 50-60→20% / <50→10%）→ 市场调整（BULL ×1.2 / BEAR ×0.2）→ 波动率调整 → Kelly（组合调整 1/√N）→ 总仓位限制 → 最终 5%-40% 夹紧。参数：半凯利 fraction 0.5、单只上限 40%、组合上限 80%、最小交易 10 笔、默认胜率 0.55、默认盈亏比 1.5。

> 两条线的上限不同（25% vs 40%/80%）：调研线是单规则统计口径，产品线是组合管理口径。生产以产品线为准；调研线的 25% 是其回测结论的边界条件。

## 6. 信号质量约束（调研线准入门槛，详见 06）

- 规则入库门槛：**≥6 个月窗口验证**（3 个月结论有 5 项在半年翻转）
- 最小样本：单规则信号 **≥30 笔**才允许启用（不足则标"样本不足"）
- 月度稳定性：任何规则按月剖切不得出现"单月贡献全部盈利"
- 双池一致性：主池与扩展池方向必须一致（泛化性检验）
- 样本量分档：≥100 可进采纳配置 / 30-99 方向性参考（评级 ≤B）/ 10-29 仅记录 / <10 不给 Kelly 仓位

### 7.3 ETF 持仓成分股监控（2026-10-18 新增需求）

**动机**：热门 ETF 的季度持仓变化（成分股进出、增减持）是机构资金流向的公开代理指标，先于季报文字解读发现结构变化。

| 编号 | 需求 | 口径 |
|---|---|---|
| ETF-H1 | 监控范围 | 14 只热门 ETF（与 ETF 行情监控同清单 `services/etf_monitor.py` 的 `HOT_ETFS`：宽基 4 + 中小盘 2 + 科创/创业 2 + 行业主题 6）；每只取季报**前 100 大持仓** |
| ETF-H2 | 变化维度 | ① 数量：持股数（万股）环比相对变化 ② 方向：新进/退出/增持/减持/持平 ③ 价格：持仓市值（万元）与权重（占净值比例）变化；可选叠加成分股实时价（API 侧） |
| ETF-H3 | 数据来源与频率 | 天天基金 F10 持仓接口（`FundArchivesDatas.aspx?type=jjcc`），**季度更新**；盘后每日检查一次（含周末，季报披露日不固定），发现新季度才计算与推送 |
| ETF-H4 | 推送条件 | 新进/退出（市值 ≥1000 万元）｜权重变化 ≥0.3pct｜持股数变化 ≥10% 且权重同向变化 ≥0.1pct（剔除 ETF 份额申赎导致的整体缩放）；单只 ETF 一次推送，最多各方向列 10 只 |
| ETF-H5 | 去重与幂等 | Redis `etf_holdings:check_date` 每日只检查一次；已处理季度不重复 diff（`etf_holdings:latest:{code}` 记录最新季） |
| ETF-H6 | 数据质量断言 | 两季反推基金净值跳变 >50% 时记 warning 并在推送文案中标注"持股数变化或含数据源异常"（实测 2026Q1 部分 ETF 存在此现象，见 02 §3.6） |

**边界（诚实声明）**：① "退出"= 退出前 100 大持仓，**不等于清仓**（季报只披露前 N 大，未披露部分无法判定）② 主动权益基金仅披露十大重仓，本监控对指数 ETF 才有完整持仓口径 ③ 持仓为季报截止日数据，与实时持仓有最多一个季度的时滞。

### 7.4 早间财经新闻推送（2026-10-18 新增需求，D 线）

**动机**：盘前 9:15 汇总隔夜至当日早间的多源财经新闻，按板块分组推送，服务当日交易决策的信息输入。

| 编号 | 需求 | 口径 |
|---|---|---|
| N1 | 推送时间 | 每个自然日 **9:15**（含周末与节假日；周一覆盖周末全部新闻）。执行窗口 9:14-9:35，`news:check_date` 每日只推一次 |
| N2 | 去重 | 三层：① 规范化标题（去空白/标点/【】前缀/大小写）SHA1 精确去重，指纹跨推送保留 48h ② 标题近似去重（difflib 相似度 ≥0.85，跨源改写在所难免）③ 同一事件多源报道保留优先级最高的源（东财>同花顺>新浪>RSS>X>通达信） |
| N3 | 数据来源 | 尽量多源：东财快讯（101重要/102全球/103公司三栏目）、同花顺快讯、新浪财经 7×24 直播为常驻免费源；通用 RSS/Atom 适配器可配置追加；X(Twitter) API v2 与通达信 MCP 为凭据门控源（默认关闭，配置后启用）。**实测不可用**：财联社电报（新版需签名）、金十数据（502）——见 02 §3.7 |
| N4 | 板块分组 | 关键词字典分类（25 个行业/主题板块 + 宏观政策 + 全球市场），一条新闻可归多个板块（上限 3 个，按命中关键词数排序），未匹配入"综合要闻"；源标签（同花顺 tagInfo/新浪 tag）参与匹配加权 |
| N5 | 推送内容与限量 | 钉钉 markdown：时间窗 + 新增条数 + 去重剔除数 + 来源统计 + 按板块分组的条目（时间/来源/标题/链接）；单板块最多 6 条，最多 8 个板块，其余板块计数汇总一行；文案总长 15000 字符截断 |
| N6 | 时间窗 | 默认自**上次成功推送时刻**起（周一自动覆盖周末）；无历史记录时回看 20 小时（`NEWS_WINDOW_HOURS`） |
| N7 | 无新增不推送 | 时间窗内全部条目均被去重命中时不推送（仅推进窗口记录），避免空推送打扰 |

**边界（诚实声明）**：① 板块分类是关键词匹配不是 NLP，存在错分与漏分，按板块浏览而非精确归类 ② 各源免费接口非承诺 SLA，随时可能变更或限流，单源故障自动降级（其余源照常推送）③ X 与通达信源需用户自备凭据，未经验证链路首次启用时需人工核对 ④ 新闻内容版权归原源所有，推送仅含标题+摘要+原文链接。

### 7.5 代码一致性守护（CodeGuard，2026-10-18 新增需求，E 线）

**动机**：原项目曾出现「代码与实际股票不匹配」事故——同一股票在不同数据源被解析成不同标准代码（典型：510300 沪深300ETF 在东财源为 510300.SH，腾讯源因 `startswith('6')` 推断错判为 510300.SZ；北交所 920819 在东财/新浪源全部错判市场），造成 Redis `quote:{code}` 缓存同股双键分裂、ETF 监控按 code 匹配失效持续显示"数据获取中"、持仓 diff 键错乱。本需求把该类事故从"事后人工发现"变为"开盘前自动拦截"。

| 编号 | 需求 | 口径 |
|---|---|---|
| CG1 | 统一代码标准 | 全项目代码格式唯一真相 `utils/code_utils.py`：标准码 `XXXXXX.SH/.SZ/.BJ`；`normalize_code/to_secid/to_tencent_code/to_sina_code` 集中管理，数据源禁止散落隐式转换。规则表：SH=6/5/9 开头（主板/科创/ETF/B股），SZ=0/1/2/3 开头，BJ=4/8/92 开头（含 920 北交所新段） |
| CG2 | 数据源解析原则 | 行情源一律用**数据源自带市场标识**解析（腾讯行首 `v_sh/sz/bj`、东财 `f13` 市场字段、新浪行首前缀），静态前缀规则仅兜底（天天基金 F10 HTML、手写配置等无市场字段场景）；无法识别的代码拒绝入库并告警，不静默通过 |
| CG3 | 盘前静态校验 | 交易日 9:00-9:15（PRE_MARKET）执行：① 格式合法性 ② 市场标记（本地后缀 vs 权威源市场）③ 存在性（权威源查无=疑似退市/错码）④ 名称新鲜度（本地 vs 权威，ST/简称归一化后比较）；Redis `code_guard:check_date_static` 每日一次 |
| CG4 | 集合竞价缓存校验 | 交易日 9:15-9:25（SELF_CHECK）顺便执行：竞价虚拟匹配价 vs `quote:{code}` 缓存昨收的连续性校验，跳空 >11%（涨跌停 10%+缓冲）判定缓存串号；Redis `code_guard:check_date_auction` 每日一次 |
