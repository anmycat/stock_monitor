# 25 系统效率评估与架构选型分析（2026-10-25）

> 结论先行：**维持 Python 架构，不做语言迁移**。系统是 I/O 密集型（外部行情 API + LLM + Webhook），
> 实测负载 0.14/2 核、三服务合计 513MB/1607MB，语言运行时不是瓶颈；
> 唯一高价值增量是补 **SQLite 持久层**（信号/回测历史审计），详见 §5。

## 2. 负载画像（决定架构的根本因素）

| 维度 | 实测特征 | 架构含义 |
|---|---|---|
| 计算密度 | 策略打分为 YAML 阈值 + pandas 百行级运算 | 微秒-毫秒级，无计算瓶颈 |
| I/O 密度 | 每轮扫描：TDX/腾讯/新浪/东财 HTTP + LLM API + 钉钉 Webhook | 90%+ 耗时在外部往返 |
| 并发量 | 个人工具，1 用户；API 请求分钟级 | 无需高并发架构 |
| 数据量 | 日频信号/评估，KB-MB 级/天 | 单机存储绰绰有余 |
| 时效要求 | 信号推送分钟级延迟可接受 | 非低延迟交易系统 |

**判断：I/O 绑定 + 低并发 + 轻计算。语言运行时的原始性能（Java JIT / Node 事件循环）在此负载下没有可兑现的优势。**

## 3. 语言选型对比（Python vs Java vs Node.js）

| 维度 | Python（现状） | Java | Node.js |
|---|---|---|---|
| 量化生态 | **pandas/numpy/pytdx/hmmlearn，全套现成** | 无对口生态（talib 绑定老旧） | danfojs 远不成熟 |
| 迁移成本 | 0 | **106 模块全重写 + TDX 协议自实现 + 策略逻辑移植（人月级）** | 同上，且 HMM/Kelly 数值库匮乏 |
| JVM/运行时开销 | 143-228MB/进程 | JVM 基础 256-512MB，1.6GB 机器更紧 | ~80-120MB |
| I/O 并发 | 异步够用（httpx）+ 3 进程拆分 | 虚线程强，但用不上 | 事件循环强，但用不上 |
| 运维复杂度 | PEP 668 已用探针式部署解决 | WAR/JAR + JVM 调优 + 监控栈 | npm 依赖树 + 原生模块编译 |
| 数值计算 | pandas 向量化直接可用 | 需重写为数组运算 | 无向量化，纯 JS 循环更慢 |
| 团队技能 | 现有代码即文档 | 零积累 | 零积累 |

**结论：迁移的收益（运行时性能）在本负载下为零，成本（重写 + 生态重建 + 数值库缺失）为数月人月。明确否决。**

## 4. 数据库选型

| 方案 | 适用性 | 结论 |
|---|---|---|
| Redis（现状） | 缓存/相位/冷却，TTL 语义正确 | **保留**，本轮已修复自愈缺陷 |
| SQLite | 信号历史/回测结果/评估归档，单文件零运维，WAL 并发读 | **建议新增**（§5） |
| PostgreSQL | 多写者/多端共享才需要 | 过重，个人单机无收益 |
| MySQL | 同上 | 过重 |

## 5. 建议的增量改进（按价值排序，均非重写）

1. **SQLite 持久层（高价值）**：信号表（code/action/score/strategy/kelly/资金流/时间戳）、
   回测评估表、总结归档表。解决当前「信号只在 Redis 活 15 分钟、历史靠 JSON 散落」
   的审计缺口。`aiosqlite` 或同步 sqlite3（写入量 KB/天，同步足够）。
2. **数据源请求合并（中价值）**：盘中多策略对同一代码取数时按 TTL 合并（已有部分缓存，
   可扩展到请求粒度 in-flight 合并，与本轮单飞锁同思路）。
3. **东财限流应对（已缓解）**：资金流失败负缓存 10 分钟可自愈；如需更高可用性，
   可将资金流降级为「仅交易时段首次 BUY 时取数」。
4. **不建议**：微服务化、消息队列、分库分表、K8s——负载画像完全不支撑。

## 6. 本轮效率相关修复清单（已验证）

| 修复 | 效果 |
|---|---|
| /api/signals 单飞锁 + worker 预热 + TTL 900 | 冷扫并发堆积 → 1 扫描 + 503 快失败；温缓存 2.5ms |
| Redis 不可用护栏 | 故障期 3ms 拒绝冷扫（原 30s+ 挂起且争抢 TDX） |
| RedisCache 节流重连自愈 | 抖动后进程级缓存自动恢复（原永久瘫痪至重启） |
| 4 处重构遗留导入断裂 | 函数内延迟导入静默失败 → 实际功能失效（板块加分/Kelly 动态参数/新闻 settings） |

## 7. 结论

Python + FastAPI + Redis（+建议 SQLite）的架构与负载画像匹配，效率瓶颈全在外部 API
而非运行时。继续沿「小步增量 + 每轮验收六件套」迭代，不启动语言/框架迁移。
