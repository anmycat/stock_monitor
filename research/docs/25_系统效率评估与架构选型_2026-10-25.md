# 25 系统效率评估与架构选型分析（2026-10-25）

> 结论先行：**维持 Python 架构，不做语言迁移**。系统是 I/O 密集型（外部行情 API + LLM + Webhook），
> 实测负载 0.14/2 核、三服务合计 513MB/1607MB，语言运行时不是瓶颈；
> 唯一高价值增量是补 **SQLite 持久层**（信号/回测历史审计），详见 §5。

## 1. 实测效率数据（ECS，2026-10-25 00:22）

### 1.1 API 响应时间（温缓存，3 次采样）

| 端点 | 延迟 | 说明 |
|---|---|---|
| /api/health | 2.0-2.4ms | 相位+数据源状态 |
| /api/market | 2.5-2.7ms | 5575 只全市场快照（缓存） |
| /api/signals | 2.5ms | 温缓存；冷缓存单飞扫描 1.5s |
| /api/evaluation/runs | 4.1-5.4ms | 回测评估列表 |

### 1.2 服务资源（2 核 / 1607MB 机器）

| 服务 | RSS | 角色 |
|---|---|---|
| quant-api | 228MB | FastAPI + uvicorn |
| quant-worker | 143MB | 相位驱动主循环 |
| quant-beat | 142MB | APScheduler 监控 |
| **合计** | **513MB（32%）** | load average 0.14/0.20/0.19 |

### 1.3 数据管线

- 冷扫描（无缓存）：~1.5s/轮（80 只活跃股 + 市场分析 + 板块）
- 全市场覆盖：5575 只（腾讯主源 + 新浪 5576 校验 + TDX 分钟线）
- Redis：3.51MB / 184 键；故障期降级 + 5s 节流探针自愈（本轮修复）
- LLM：DeepSeek V4 + MiMo v2.5 双模型加权，竞价/总结场景 2-5s/次

## 2. 负载画像（决定架构的根本因素）

| 维度 | 实测特征 | 架构含义 |
|---|---|---|
| 计算密度 | 策略打分为 YAML 阈值 + pandas 百行级运算 | 微秒-毫秒级，无计算瓶颈 |
| I/O 密度 | 每轮扫描：TDX/腾讯/新浪/东财 HTTP + LLM API + 钉钉 Webhook | 90%+ 耗时在外部往返 |
| 并发量 | 个人工具，1 用户；API 请求分钟级 | 无需高并发架构 |
| 数据量 | 日频信号/评估，KB-MB 级/天 | 单机存储绰绰有余 |
| 时效要求 | 信号推送分钟级延迟可接受 | 非低延迟交易系统 |

**判断：I/O 绑定 + 低并发 + 轻计算。语言运行时的原始性能（Java JIT / Node 事件循环）在此负载下没有可兑现的优势。**

## 3. 语言选型对比（Python vs Java vs Node.js）

| 维度 | Python（现状） | Java | Node.js |
|---|---|---|---|
| 量化生态 | **pandas/numpy/pytdx/hmmlearn，全套现成** | 无对口生态（talib 绑定老旧） | danfojs 远不成熟 |
| 迁移成本 | 0 | **106 模块全重写 + TDX 协议自实现 + 策略逻辑移植（人月级）** | 同上，且 HMM/Kelly 数值库匮乏 |
| JVM/运行时开销 | 143-228MB/进程 | JVM 基础 256-512MB，1.6GB 机器更紧 | ~80-120MB |
| I/O 并发 | 异步够用（httpx）+ 3 进程拆分 | 虚线程强，但用不上 | 事件循环强，但用不上 |
| 运维复杂度 | PEP 668 已用探针式部署解决 | WAR/JAR + JVM 调优 + 监控栈 | npm 依赖树 + 原生模块编译 |
| 数值计算 | pandas 向量化直接可用 | 需重写为数组运算 | 无向量化，纯 JS 循环更慢 |
| 团队技能 | 现有代码即文档 | 零积累 | 零积累 |

**结论：迁移的收益（运行时性能）在本负载下为零，成本（重写 + 生态重建 + 数值库缺失）为数月人月。明确否决。**

## 4. 数据库选型

| 方案 | 适用性 | 结论 |
|---|---|---|
| Redis（现状） | 缓存/相位/冷却，TTL 语义正确 | **保留**，本轮已修复自愈缺陷 |
| SQLite | 信号历史/回测结果/评估归档，单文件零运维，WAL 并发读 | **建议新增**（§5） |
| PostgreSQL | 多写者/多端共享才需要 | 过重，个人单机无收益 |
| MySQL | 同上 | 过重 |

## 5. 建议的增量改进（按价值排序，均非重写）

1. **SQLite 持久层（高价值）**：信号表（code/action/score/strategy/kelly/资金流/时间戳）、
   回测评估表、总结归档表。解决当前「信号只在 Redis 活 15 分钟、历史靠 JSON 散落」
   的审计缺口。`aiosqlite` 或同步 sqlite3（写入量 KB/天，同步足够）。
2. **数据源请求合并（中价值）**：盘中多策略对同一代码取数时按 TTL 合并（已有部分缓存，
   可扩展到请求粒度 in-flight 合并，与本轮单飞锁同思路）。
3. **东财限流应对（已缓解）**：资金流失败负缓存 10 分钟可自愈；如需更高可用性，
   可将资金流降级为「仅交易时段首次 BUY 时取数」。
4. **不建议**：微服务化、消息队列、分库分表、K8s——负载画像完全不支撑。

## 6. 本轮效率相关修复清单（已验证）

| 修复 | 效果 |
|---|---|
| /api/signals 单飞锁 + worker 预热 + TTL 900 | 冷扫并发堆积 → 1 扫描 + 503 快失败；温缓存 2.5ms |
| Redis 不可用护栏 | 故障期 3ms 拒绝冷扫（原 30s+ 挂起且争抢 TDX） |
| RedisCache 节流重连自愈 | 抖动后进程级缓存自动恢复（原永久瘫痪至重启） |
| 4 处重构遗留导入断裂 | 函数内延迟导入静默失败 → 实际功能失效（板块加分/Kelly 动态参数/新闻 settings） |

## 7. 结论

Python + FastAPI + Redis（+建议 SQLite）的架构与负载画像匹配，效率瓶颈全在外部 API
而非运行时。继续沿「小步增量 + 每轮验收六件套」迭代，不启动语言/框架迁移。

## 8. 增补：Rust 化 / 分层改造评估（2026-11-21，D74 后回填）

> 触发：用户「今天调研发现 Rust 在协议兼容方面有优势，考虑整个项目架构是否 Rust 化改造或分层改造」。
> 本节用**最近行情数据实测**回答，不套旧结论；对应文件就地更新（纪律③），不新开报告。

### 8.1 实测数据（2026-11-21 晚，本地真机，可复现）

| 维度 | 实测 | 来源 |
|---|---|---|
| eltdx 是否 Rust 原生 | ✅ `eltdx/_native.abi3.so`（Rust 编译的 CPython 扩展，非纯 Python） | `pip install eltdx==3.3.5`，py3.13 venv |
| eltdx 日K 10 票批量 | **472.9 ms**（≈47 ms/票，TCP 7709） | 真机取 `sz000001/sh600519/...`×10，qfq 30 根 |
| 新浪 HTTP 日K 10 票批量 | **2850.1 ms**（≈285 ms/票，HTTPS） | 同 10 票同口径对照 |
| 相对速度 | **Rust/TCP ≈ 6.0× 快于 Python/HTTP** | 两者数据一致（D73 已验证收盘价差 0.0） |
| Python 纯计算：单票 pandas 打分 | **≈0.7 ms/票**（1000 次 707.9 ms） | 项目 venv py3.9 pandas 2.2.0 |
| 既有负载画像（docs/25 §1-2） | CPU load 0.14/2 核、I/O 占 90%+、API 2-5 ms | ECS 10-25 实测 |

### 8.2 结论：不做全量 Rust 化，但「分层」早已落地且是正解

- **全量 Rust 化否决**：10-25 结论仍成立——106 模块 + pandas/数值生态 + 策略/回测/LLM 全重写，迁移人月级，收益（运行时性能）在 I/O 密集型个人工具下无兑现。今天的 6× 加速来自 **TCP vs HTTPS 协议栈+连接开销**，不是「Rust 编译」本身可泛化到全项目的红利。
- **真正的收益点是「协议实现层」**：pytdx 客户端恒空 → eltdx（Rust 7709）取真实数据（D73 已证），这才是不可替代的能力。而它**以 Python wheel 形式提供**（`_native.abi3.so`）——即 Rust 只负责协议编解码/连接，Python 保留编排/策略/计算/API。**这正是分层架构**。
- **D74 已经完成分层**：`data/sources/eltdx_client.py`（Python 编排）+ `_native.abi3.so`（Rust 协议核）双层；daily/minute 末位兜底 + market_alert 旁路证据均走这层，零信号影响、D41 字节级一致。计算仍 Python（0.7 ms/票，占比可忽略）。

### 8.3 若未来要深化（P3，非当前立项）

| 方向 | 做法 | 收益 | 触发条件 |
|---|---|---|---|
| 高频/批量取数下沉 | 用 eltdx 原生批量与连接池替代 Python 逐票循环 | 批量延迟进一步下降（当前 47 ms/票含串行握手） | 单轮取数成为瓶颈（当前不是） |
| 协议网关独立进程 | eltdx HTTP/MCP 网关前置，Python 只做策略 | 进程隔离、多入口 | 多端消费同一数据；与 N-12 MCP 同源，暂缓 |
| 完全不建议 | 策略/回测/API/LLM 全 Rust 重写 | 负收益（生态与迁移成本） | 除非转商业高并发低延迟系统 |

**一句话**：Rust 化 = 把「协议兼容」这一层交给 Rust（已由 eltdx wheel 实现）；分层改造 = 保持 Python 主控、Rust 只做协议/连接。当前架构已是这个形态，**无需重构，只需按需在 eltdx 策略层做增量**。
