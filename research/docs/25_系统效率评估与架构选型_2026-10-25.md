# 25 系统效率评估与架构选型分析（2026-10-25）

> 结论先行：**维持 Python 架构，不做语言迁移**。系统是 I/O 密集型（外部行情 API + LLM + Webhook），
> 实测负载 0.14/2 核、三服务合计 513MB/1607MB，语言运行时不是瓶颈；
> 唯一高价值增量是补 **SQLite 持久层**（信号/回测历史审计），详见 §5。

## 2. 负载画像（决定架构的根本因素）

| 维度 | 实测特征 | 架构含义 |
|---|---|---|
| 计算密度 | 策略打分为 YAML 阈值 + pandas 百行级运算 | 微秒-毫秒级，无计算瓶颈 |
| I/O 密度 | 每轮扫描：TDX/腾讯/新浪/东财 HTTP + LLM API + 钉钉 Webhook | 90%+ 耗时在外部往返 |
| 并发量 | 个人工具，1 用户；API 请求分钟级 | 无需高并发架构 |
| 数据量 | 日频信号/评估，KB-MB 级/天 | 单机存储绰绰有余 |
| 时效要求 | 信号推送分钟级延迟可接受 | 非低延迟交易系统 |

**判断：I/O 绑定 + 低并发 + 轻计算。语言运行时的原始性能（Java JIT / Node 事件循环）在此负载下没有可兑现的优势。**

## 3. 语言选型对比（Python vs Java vs Node.js）

| 维度 | Python（现状） | Java | Node.js |
|---|---|---|---|
| 量化生态 | **pandas/numpy/pytdx/hmmlearn，全套现成** | 无对口生态（talib 绑定老旧） | danfojs 远不成熟 |
| 迁移成本 | 0 | **106 模块全重写 + TDX 协议自实现 + 策略逻辑移植（人月级）** | 同上，且 HMM/Kelly 数值库匮乏 |
| JVM/运行时开销 | 143-228MB/进程 | JVM 基础 256-512MB，1.6GB 机器更紧 | ~80-120MB |
| I/O 并发 | 异步够用（httpx）+ 3 进程拆分 | 虚线程强，但用不上 | 事件循环强，但用不上 |
| 运维复杂度 | PEP 668 已用探针式部署解决 | WAR/JAR + JVM 调优 + 监控栈 | npm 依赖树 + 原生模块编译 |
| 数值计算 | pandas 向量化直接可用 | 需重写为数组运算 | 无向量化，纯 JS 循环更慢 |
| 团队技能 | 现有代码即文档 | 零积累 | 零积累 |

**结论：迁移的收益（运行时性能）在本负载下为零，成本（重写 + 生态重建 + 数值库缺失）为数月人月。明确否决。**

## 4. 数据库选型

| 方案 | 适用性 | 结论 |
|---|---|---|
| Redis（现状） | 缓存/相位/冷却，TTL 语义正确 | **保留**，本轮已修复自愈缺陷 |
| SQLite | 信号历史/回测结果/评估归档，单文件零运维，WAL 并发读 | **建议新增**（§5） |
| PostgreSQL | 多写者/多端共享才需要 | 过重，个人单机无收益 |
| MySQL | 同上 | 过重 |

## 5. 建议的增量改进（按价值排序，均非重写）

1. **SQLite 持久层（高价值）**：信号表（code/action/score/strategy/kelly/资金流/时间戳）、
   回测评估表、总结归档表。解决当前「信号只在 Redis 活 15 分钟、历史靠 JSON 散落」
   的审计缺口。`aiosqlite` 或同步 sqlite3（写入量 KB/天，同步足够）。
2. **数据源请求合并（中价值）**：盘中多策略对同一代码取数时按 TTL 合并（已有部分缓存，
   可扩展到请求粒度 in-flight 合并，与本轮单飞锁同思路）。
3. **东财限流应对（已缓解）**：资金流失败负缓存 10 分钟可自愈；如需更高可用性，
   可将资金流降级为「仅交易时段首次 BUY 时取数」。
4. **不建议**：微服务化、消息队列、分库分表、K8s——负载画像完全不支撑。

## 6. 本轮效率相关修复清单（已验证）

| 修复 | 效果 |
|---|---|
| /api/signals 单飞锁 + worker 预热 + TTL 900 | 冷扫并发堆积 → 1 扫描 + 503 快失败；温缓存 2.5ms |
| Redis 不可用护栏 | 故障期 3ms 拒绝冷扫（原 30s+ 挂起且争抢 TDX） |
| RedisCache 节流重连自愈 | 抖动后进程级缓存自动恢复（原永久瘫痪至重启） |
| 4 处重构遗留导入断裂 | 函数内延迟导入静默失败 → 实际功能失效（板块加分/Kelly 动态参数/新闻 settings） |

## 7. 结论

Python + FastAPI + Redis（+建议 SQLite）的架构与负载画像匹配，效率瓶颈全在外部 API
而非运行时。继续沿「小步增量 + 每轮验收六件套」迭代，不启动语言/框架迁移。

> 触发：用户「今天调研发现 Rust 在协议兼容方面有优势，考虑整个项目架构是否 Rust 化改造或分层改造」。
> 本节用**最近行情数据实测**回答，不套旧结论；对应文件就地更新（纪律③），不新开报告。

### 8.1 实测数据（2026-11-21 晚，本地真机，可复现）

| 维度 | 实测 | 来源 |
|---|---|---|
| eltdx 是否 Rust 原生 | ✅ `eltdx/_native.abi3.so`（Rust 编译的 CPython 扩展，非纯 Python） | `pip install eltdx==3.3.5`，py3.13 venv |
| eltdx 日K 10 票批量 | **472.9 ms**（≈47 ms/票，TCP 7709） | 真机取 `sz000001/sh600519/...`×10，qfq 30 根 |
| 新浪 HTTP 日K 10 票批量 | **2850.1 ms**（≈285 ms/票，HTTPS） | 同 10 票同口径对照 |
| 相对速度 | **Rust/TCP ≈ 6.0× 快于 Python/HTTP** | 两者数据一致（D73 已验证收盘价差 0.0） |
| Python 纯计算：单票 pandas 打分 | **≈0.7 ms/票**（1000 次 707.9 ms） | 项目 venv py3.9 pandas 2.2.0 |
| 既有负载画像（docs/25 §1-2） | CPU load 0.14/2 核、I/O 占 90%+、API 2-5 ms | ECS 10-25 实测 |

### 8.2 结论：不做全量 Rust 化，但「分层」早已落地且是正解

- **全量 Rust 化否决**：10-25 结论仍成立——106 模块 + pandas/数值生态 + 策略/回测/LLM 全重写，迁移人月级，收益（运行时性能）在 I/O 密集型个人工具下无兑现。今天的 6× 加速来自 **TCP vs HTTPS 协议栈+连接开销**，不是「Rust 编译」本身可泛化到全项目的红利。
- **真正的收益点是「协议实现层」**：pytdx 客户端恒空 → eltdx（Rust 7709）取真实数据（D73 已证），这才是不可替代的能力。而它**以 Python wheel 形式提供**（`_native.abi3.so`）——即 Rust 只负责协议编解码/连接，Python 保留编排/策略/计算/API。**这正是分层架构**。
- **D74 已经完成分层**：`data/sources/eltdx_client.py`（Python 编排）+ `_native.abi3.so`（Rust 协议核）双层；daily/minute 末位兜底 + market_alert 旁路证据均走这层，零信号影响、D41 字节级一致。计算仍 Python（0.7 ms/票，占比可忽略）。

### 8.3 若未来要深化（P3，非当前立项）

| 方向 | 做法 | 收益 | 触发条件 |
|---|---|---|---|
| 高频/批量取数下沉 | 用 eltdx 原生批量与连接池替代 Python 逐票循环 | 批量延迟进一步下降（当前 47 ms/票含串行握手） | 单轮取数成为瓶颈（当前不是） |
| 协议网关独立进程 | eltdx HTTP/MCP 网关前置，Python 只做策略 | 进程隔离、多入口 | 多端消费同一数据；与 N-12 MCP 同源，暂缓 |
| 完全不建议 | 策略/回测/API/LLM 全 Rust 重写 | 负收益（生态与迁移成本） | 除非转商业高并发低延迟系统 |

**一句话**：Rust 化 = 把「协议兼容」这一层交给 Rust（已由 eltdx wheel 实现）；分层改造 = 保持 Python 主控、Rust 只做协议/连接。当前架构已是这个形态，**无需重构，只需按需在 eltdx 策略层做增量**。

**8.4.2 关键工程细节（踩坑记录，供后续下沉内核复用）**

1. **numpy `pairwise_sum` 必须复刻**：种子均值用 `mean` 时，若按朴素顺序累加，
   f64 最后一位会不同 → RSI 差 1 ulp → 阈值边界处信号翻转。Rust 侧按
   numpy `loops.c.src` 的 8 路展开 + n≤128 规则 + n>128 递归对半实现。
2. **`delta.where(delta > 0, 0.0)` 的真实语义**：首根 NaN 差分被 `where`
   **替换成 0.0**（不是保留 NaN），因此 gain/loss 长度 == `len(closes)`；
   第一版按「过滤 NaN」实现导致 n=15 时 RSI 69.67 vs 69.55 的实差，
   被 `test/test_rust_accel.py` 的位级断言当场抓住。
3. **macOS 链接**：PyO3 扩展在 macOS 需 `-C link-arg=-undefined -C link-arg=dynamic_lookup`
   （脚本已按平台分支处理）；Linux 无需。
4. **密钥扫描误报**：`Cargo.lock` 的 `checksum` 与 cargo 构建产物目录会被
   `scan_secrets.py` 判为十六进制密钥 → 已加入 `EXEMPT_PATHS`（锁文件必须入库以复现构建）。

**8.4.3 验证与诚实边界**

- 专项测试 `test/test_rust_accel.py`（11 例）：随机游走 5/13/14/15/240/2000 根、
  含 NaN 脏数据、全涨/全跌/横盘边界、模块级整链 `calculate_indicators` 全字段
  **位级相等**（`struct.pack('<d')` 比较，不是 allclose）。
- **D41 双跑 `5cb993e` vs 工作树**：129 日 × 27 票、530 笔信号，两个 JSON
  `sha256=72c728d9…0467` **完全相同**（`cmp` 逐字节一致）→ Rust 下沉零信号漂移。
- **诚实边界**：本系统的耗时 95% 以上在 HTTP 取数与 pandas 向量化，Python 级
  循环本来就只占微秒级；RSI 单次调用实测 Rust ≈25 µs vs Python ≈31 µs。
  **本轮收益是「有了自己的 Rust 层与构建链路」这件事本身**（后续可继续把
  平台天数/连板/筹码等循环继续下沉），而不是显著提速——不夸大成加速故事。

**8.4.4 仍不建议的方向**

- 全量 Rust 重写（§8.2 结论不变）。
- 把策略/风控/回测逻辑搬进 Rust：这些是「会被反复改的业务语义」，
  放 Rust 会让每次调参都变成跨语言发布；保持「Rust 只做数值内核，语义留 Python」。

### 8.5 专项评估（2026-11-22，D78 后）：「整个项目用 Rust 重写」的意义与负面

> 用户指定课题：相比目前 Python 为主的 coding，整个项目改用 Rust 的意义与负面。
> 本节全部论据取自本项目实测/统计，不引用印象。结论维持 §8.2，本节给出完整论证。

**8.5.1 本项目的 workload 实测画像（重评的起点）**

| 维度 | 实测值 | 来源 |
|---|---|---|
| 代码规模 | quant_engine 129 个 .py / 24,131 行；44 个模块直接 import pandas | 2026-11-22 统计 |
| 计算耗时占比 | 每轮扫描 **90%+ 耗时在外部 I/O**（腾讯/新浪/东财 HTTP + LLM API + 钉钉），纯计算微秒-毫秒级 | §2 负载画像（ECS 实测） |
| 单票指标计算 | Python 纯计算 **0.7 ms/票**（27 票池） | §8.1 实测 |
| Rust 内核单次 | RSI 单次 Rust ≈25 µs vs Python ≈31 µs（省 6 µs） | D78 微基准 |
| 外部等待典型值 | 东财全局限速 ≥1s/请求（D68）；连板天梯一次 ~6.6 s（D74）；LLM 响应秒级 | docs/36、docs/45 |

| 机器 | 2 核 / 1.6 GB（+2G swap，D78 补做） | docs/37/38 |

**8.5.2 意义（Rust 全量重写能带来什么）——逐条对照本项目兑现度**

| # | Rust 的真实优势 | 在本项目的兑现度 |
|---|---|---|
| 1 | 无 GIL + 零成本抽象 + SIMD，CPU 密集场景 10-100× | **≈0**。瓶颈是网络等待（90%+）；计算端 RSI 仅省 6µs，即便 27 票全指标下沉也只有亚毫秒级收益 |
| 2 | 内存安全、无 GC 抖动 | **≈0**。worker 常驻 ~163MB、无泄漏史；Python GC 在 KB-MB 级日频数据上无可测抖动 |
| 3 | 类型系统编译期捕获错误 | **低**。项目已有 52 个测试文件 + ruff + D41 双跑门禁；历史真实事故是浮点口径、数据语义、跨进程竞态——Rust 同样要人写对，类型系统帮不上这几类 |
| 4 | 单二进制部署，无运行时依赖 | **负收益**。现网 systemd+venv 部署链已验证可靠（D77 136 文件 sha256 逐一相同）；换 Rust 反而引入交叉编译/musl-glibc 差异等新风险面 |
| 5 | fearless 并发 | **用不上**。3 进程拆分（api/worker/beat）+ httpx 异步已覆盖全部并发需求 |
| 6 | 长期性能天花板 | **唯一真实意义**：若未来扩展到全市场 5,000 票 tick 级实时扫描/L2 计算，Python 会先撞 CPU 墙——但属假设性需求，当前无立项 |

**8.5.3 负面（成本与风险）——每条都有本项目实证锚点**

1. **重写工作量为人月级 × 生态重建**：24,131 行 / 129 文件全量重写，其中 44 个模块的
   pandas DataFrame 链路（indicator→strategy→factor→report）要换成 Rust 数组库（polars 可
   迁移数据层，但语义细节如 `where` 的 NaN 行为、索引对齐、`df.attrs` 血缘标签——D66 核心
   机制——全部要重新实现）；参照 D34-D40「Python→Python 架构重构」就花了六阶段，跨语言
   重写量级至少 ×10。

2. **数值生态断层（硬伤）**：`hmmlearn`（HMM 状态识别）、`scikit-learn`、`exchange-calendars`、
   `pandas` 向量化回测在 Rust 侧均无成熟等价物（`ndarray`/`statrs` 远未覆盖）；结果必然是
   FFI 回调 Python（回到起点）或自研数值代码（引入正确性风险）。

3. **逐位等价成本被 D78 实证放大**：只下沉 4 个内核就踩了 3 个位级坑——
   ① numpy `pairwise_sum` 求和顺序决定 f64 最低位；② pandas `where` 把首根 NaN 差分替换为
   0.0（非保留），n=15 时 RSI 出现 69.6709 vs 69.5494 翻阈值偏差；③ 跨 OS 产物不可复用
   （mac .so → ECS invalid ELF header）。全项目重写意味着**每个指标、每个信号字段都要位级
   对齐**，D41 回归门禁全部重做且难度陡增——RSI 是否越过 70 阈值差 0.02 就翻转买入信号，
   这是真实资金风险，不是美学问题。

4. **迭代速度下降 = 策略 alpha 损失**：本项目最高频的改动是策略语义（D44 策略升级、S1-S7
   口径修正、Kelly 参数落库、rules JSON 调参）。Python 改完即测（分钟级闭环）；Rust 每次调
   参都是编译 + 借用检查 + 跨语言发布。**策略试错速度本身就是量化系统的核心竞争力**，
   §8.4.4 的裁定（Rust 只做数值内核、语义留 Python）正是为此。

5. **运维复杂度净增**：ECS 1.6GB 内存上 cargo release 编译 qerust 用了 2m27s（依赖刚补的
   swap 才安全）；PyO3 0.22.6 与 Python 3.14 不兼容（实测翻车后升 0.30）暴露了**构建链×
   运行时版本矩阵**这一全新维护面；rustup/crates.io 在受限网络下依赖镜像（本地曾 pypi=000、
   tuna=403，只能走 USTC），也是新增风险。

6. ~~**维护连续性**：单人项目，Python 是通用技能池；Rust 学习曲线陡，未来交接/求助成本上升。~~
   **前提订正（2026-11-22 用户指示）：本项目 coding 由 AI 大模型承担，人工学习曲线/交接成本
   不作为决策因素——此条作废，不再计入负面。重评见 §8.6。**

7. **收益/成本比的量化结论**：收益端按 §8.5.2 逐条≈0；成本端 §8.5.3 人月级 + 门禁重建 +
   生态断层 + 运维新面。**性价比显著为负**。

**8.5.4 决策与触发条件**

- **决策：维持 Python 为主体，不整体换语言**（§8.2/§8.4 结论，本节论证补全。
  **2026-11-22 晚前提订正：AI coding 场景下此结论的强度已调整，见 §8.6——仍不立项，
  但「不可行」修正为「可行但当前不划算」**）。
- 正确姿势是已落地的**分层模型**：Python 编排/策略语义/API + Rust（或 C）数值/协议内核
  （eltdx 的 TCP 协议核、qerust 的指标内核），内核对 Python 侧承诺**逐位等价 + 可回退开关**。
- **重新评估全量 Rust 化的触发条件**（满足任一才启动）：
  1. 扫描范围从 27 票扩展到全市场 ≥3,000 票且要求盘中 tick 级计算（CPU 占比实测 >30%）；
  2. 出现 Python 无法满足的硬延迟预算（如秒级 L2 决策）；
  3. 项目转为多人/商业化，且团队主力技能栈是 Rust；
  4. pandas/numpy 生态出现不可接受的停更/安全风险。
  当前四条均不成立，故搁置。

**8.6.2 四维度重评（用户指定口径）**

| 维度 | 维持 Python 主体 | 全项目 Rust | 判定 |
|---|---|---|---|
| **重构难度** | 0（现状） | AI 大幅降低"写代码"成本，但真正的难点是**语义迁移 + 逐位等价验证 + 52 测试文件门禁重建 + 44 模块 pandas 语义（NaN/索引对齐/attrs 血缘）**；这部分 AI 只能辅助，不能代签。D78 只下沉 4 个内核就暴露 3 个位级坑，全量重写的验证面是指数级 | **Python 明显占优**——AI 抹平的是打字成本，抹不平验证成本 |
| **未来迭代延展性** | 策略语义修改即改即跑；Python 数据生态现成，新数据源/新指标接入快；编译器不帮抓 AI 生成代码的逻辑错误，靠测试 | 静态类型+借用检查为 AI 生成的大规模代码提供**编译期质量网**；性能天花板高（全市场 tick 级无需换栈）；但每次策略调参引入编译回路，HMM/Kelly 等数值库需自建 | **接近平局**：Python 赢在反馈速度与生态，Rust 赢在 AI 时代的质量网与性能上限 |
| **维护容易程度** | AI 都能读改；但运行时错误（数据口径/NaN/竞态）需实跑暴露；venv+pip 依赖树+版本漂移是持续维护面（本次 PyO3 0.22→0.30 已是实证） | 编译期挡住一大类错误；**部署产物单一**（无 .env/pydantic 加载/依赖树），长期维护面更小；但数值等价回归集必须长期维护 | **略偏 Rust**（维护面更少），前提是接受验证集维护成本 |
| **ECS 配置** | 现状：2 核/1.6G + 2G swap、systemd×3、venv、.env（云知声 key/u2-flash/6000/API token）、pip 探针、cargo 运行时编译 qerust、PyO3×Python3.14 版本矩阵——**移动部件多，D77/D78 两次部署缺陷都出在这里** | 静态单二进制 + systemd×3 + 一份 config；无 Python 运行时、无 pip/cargo/.env 加载；交叉编译在开发机/CI 完成，ECS 只收二进制；内存峰值与 swap 依赖消失；**部署从"136 文件 sha256 逐一相同"退化为"3 个二进制 hash 校验"** | **Rust 明显占优**——用户点名的维度里，这是唯一一边倒的项 |

**8.6.3 订正后结论**

- **不推翻 §8.2/§8.5 的实测事实**：I/O 占比 90%+、计算 0.7ms/票、逐位等价资金风险——这三条与"谁写代码"无关，仍是否决全量重写的硬约束。
- **但调整结论强度**：从「明确否决」修正为「**当前仍不立项全量重写，但差距显著收窄**」。AI coding 抹掉了人力成本与技能门槛，让 Rust 的两个真实优势（ECS 配置极简 + 编译期质量网）第一次具备讨论价值；否决理由收窄为三条客观约束（运行时瓶颈、数值生态、逐位等价验证面）。
- **四维度净判定**：重构难度 Python 大优 / 延展性接近平局 / 维护略偏 Rust / ECS 明显偏 Rust → 综合仍不支持现在切换，但若将来触发 §8.5.4 任一条件，**AI coding 使全量重写从"不可行"变为"可行选项"**。
- **可立即兑现的部分（无需全量重写）**：把 ECS 配置简化作为独立优化目标推进——
  ① qerust 改为**目标平台（Linux x86_64）容器/CI 构建一次并缓存产物**——注意不是 mac 本机产物（D78 invalid ELF header 教训）；
  ECS 不再跑 cargo，消除 2m27s 编译峰值与 swap 依赖；glibc 兼容的 .so 缓存后可跨部署复用；
  ② 把 `.env` 敏感项收敛为 systemd `EnvironmentFile` 单一来源，减少 pydantic 加载层级；
  ③ 部署校验清单从"全量文件 sha256"按产物类型分级（代码/配置/二进制），降低 D77 类静默不同步风险。
