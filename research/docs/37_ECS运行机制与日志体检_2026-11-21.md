## 2. 发现清单（分级）

### P0 — 安全（需用户决策，本次未动）

#### P0-1 API 全网匿名暴露，且已观测到公网扫描

- `.env`：`API_HOST=0.0.0.0`、`API_PORT=8000`；`API_AUTH_TOKEN` **未在 .env 设置**（`config.py` 默认空字符串）。
- 近 7 天 `quant-api` 日志：**216 条 `WARNING: Invalid HTTP request received`**；另有公网扫描源（日志原文 IP 已脱敏）请求 `GET /error.log`（404）。
- 含义：任何能访问该 ECS 公网 8000 端口的人都可匿名调用全部 API / WS（含交易信号、持仓、日报、数据源状态），也可做畸形请求探测。`code` 侧 `audit_auth_coverage()` 41 检查 / 0 漏挂只说明**挂了鉴权装饰器**，但 token 为空时装饰器不生效。
- 建议：
  1. **短期（改防火墙，零代码风险）**：ECS 安全组把 8000 端口来源限制为白名单 IP（本地办公出口 / 跳板机），先收口暴露面；
  2. **中期（前后端同批改）**：生成 `API_AUTH_TOKEN` 写入 `.env` + 前端 `fetchAPI` 统一带 `Authorization` 头 + WS 握手带 token；
  3. 不建议只改后端不改前端（会直接断 UI，项目记忆里已有此教训）。
- 回退：安全组规则可随时删；token 启用失败只需清空 `.env` 对应键并重启 api。

### P1 — 真实缺陷 / 业务参数（已修 3 项，其余待裁定）

#### P1-1 陈旧快照最老 4.4 小时，且 `_stale` 标记「只写不拦」

- 近 7 天 worker 日志：**41 次** `get_realtime_quote` 全链降级（tencent → sina → eastmoney → stale_snapshot）后使用陈旧快照；`age` 实测 **9863 / 9883 / 15359 / 15369 / 15380 / 15765 秒**（2.7～4.4 小时）。
- 代码路径（`quant_engine/data/source_manager.py:516-553`）：`max_snapshot_age=86400`（24 小时）+ D66 跨交易日作废；同交易日内的旧快照放行，仅写 `df.attrs['_stale'] / _age_seconds`。
- 全仓检索：`_stale` / `_age_seconds` **只在 `kline_provenance.evidence()` 里透出一个展示字段**，信号生成链没有任何基于年龄的拒绝或降权逻辑。
- 判读：这是「降级优于无数据」的既有设计，但**盘中用 4 小时前的报价驱动信号**与 D64「信号价与现价分离」的严谨口径存在张力；不是崩溃性 bug，是数据质量口径风险。
- 建议（待裁定，类似 I-04 的「拒绝层」）：
  - 保守：保持放行，但在信号卡片/日报明示 `quote_age`，并把 >30 分钟的快照降级标为 `degraded`；
  - 严格：新增 `STALE_QUOTE_REJECT_SECONDS=1800` 开关，超龄快照返回 `None` 而不是旧价（会让该轮少出信号，属策略行为变更，必须用户确认）。
- 本次未改：这是策略口径决定，不是纯工程缺陷。

#### P1-2 `UNISOUND_MAX_TOKENS=2500` 致 AI 空响应（业务参数，可直接调）

- `.env` 显式 `UNISOUND_MAX_TOKENS=2500`；近 7 天 worker 日志：
  - 3 次 `云知声 U2 返回空正文（finish_reason=length），疑似 max_tokens=2500 不足以容纳思考过程`；
  - 2 次 `空响应 ... 2s/4s 后重试`；最终 1 次 `云知声 U2 失败，尝试下一个...`（级联降级到 DeepSeek）。
- 判读：U2 是带思考过程的模型，2500 token 被 reasoning 吃光，正文为空 → 日报/总结被迫换模型或走降级模板。这是**明确的业务参数配置不当**。
- 建议：把 `UNISOUND_MAX_TOKENS` 调到 **4096～6000**（先看 U2 官方上下文上限），或给 reasoning 模型单独设更高值；改后观察一个交易日 `finish_reason=length` 是否归零。
- 本次未改：需用户确认目标值与模型配额。

#### P1-3 东财 `RemoteDisconnected` 261 次，全局限速未消除该错误

- 近 7 天 worker：**261 次** `EM request failed after 3 tries: RemoteDisconnected('Remote end closed connection without response')`；另有 **76 次** `EastMoney get realtime quote error`（同类）。按日：11-16 122 次 / 11-17 54 次 / 11-19 85 次，11-20 起为 0。
- 判读：D68 的跨进程全局限速（≥1s+抖动）已上线并在 ECS 生效，但**限速解决的是请求频率，不解决长连接被对端空闲断开**：`_SESSION` keep-alive 的连接在空闲后被东财侧关闭，复用时收到 RST。11-20 起归零可能是对方策略调整，不能视为已修复。
- 建议（工程侧，可单独排期）：在 `em_get()` 里对 `RemoteDisconnected` 做「丢弃当前连接 → 新建连接 → 重试一次」的定向恢复（与现有 3 次通用重试区分），并记录恢复次数到 Redis 供健康面板观察。**不改评分/信号逻辑**。
- 本次未改：需用户确认是否纳入下一迭代。

**运行时实证（2026-11-21，回答「东财机制是否已失效」）** —— 结论：**主体没失效，抖动这一招失效了，RST 属机制能力边界**：

| 机制 | 核查证据 | 判定 |
|---|---|---|
| ①限速 + ③共用连接 | ECS 现网 `JITTER_RANGE=(0.15,0.6)`、`_SESSION` 模块级、唯一入口 `em_get()` 内部调用 `_THROTTLE.wait()`、`attach_global_throttle` 注入 2 处、`EM_GLOBAL_THROTTLE=True` 全部在位；11-14 重启后仍有 **4 条 `[EM] 跨进程全局限速已启用`** | **未失效** |
| 跨进程 Redis 预约 | 近 7 天 `全局限速预约失败` 告警 **0 条**（若 Redis 异常会按 30s 节流告警并退回 D53 进程内锁）；生产键 `em:throttle:next_allowed` TTL=-2 是**非交易时段自然过期**，不是故障 | **未失效** |
| ②随机抖动 | 用独立探针键执行现网 Lua（不碰生产键），`gap=1.37` 连续三次返回 **`0 / 1 / 2`（全整数）**，非期望的 1.37+ 浮点 | **已失效**：Redis Lua 把浮点返回值整数化 → 抖动被抵消，节奏退化为固定整数秒；本地已修（见 P1-5），ECS 未部署 |
| 非交易时段静默（截图第 2 条） | `session_gate.is_quote_window()` 限制行情访问在 9:00-11:30/13:00-15:05；静默跳过**本身不打日志**，故日志 0 条不能证伪；RST 全部落在交易时段 09-14 时，间接印证静默有效 | **未见失效证据** |
| RST 成因 | 按小时：11-16 09时87次/13时48次、11-17 09时37次/10时28次、11-19 09时63次/14时29次；**11-20 起 0 次**。呈交易时段批次性爆发而非全天均匀 | 是**连接空闲被对端批量回收**的典型形态，不是持续风控封禁；限速管「请求频率」不覆盖「对端主动断连」，属机制能力边界，需新增 RST 定向恢复（不推倒重来） |

### P2 — 运维风险 / 优化

#### P2-1 内存容量与无 Swap
- 物理 1.6 GiB、Swap **0**；三服务 `MemoryMax` 合计 **1.5 GiB**（api 500M + worker 700M + beat 300M），当前 RSS 合计 813 MB，available 559 MB。
- 若 worker 继续增长触顶 700M，systemd 会直接 OOM-kill 该服务（虽然 `Restart=always` 会拉起，但会丢内存态快照与限速预约）。7 天内无 OOM 记录，`NRestarts=0`。
- 建议：加 512 MB swap 作为缓冲（无需改代码）；或把 worker `MemoryMax` 调到 800M 并配合监控。属容量规划，非紧急。

#### P2-2 SQLite WAL 4 MB 未 checkpoint
- `history.db` 1.0 MB / `history.db-wal` 4.0 MB / `-shm` 32 KB；WAL 是主库 4 倍。
- 风险：若备份脚本只拷 `history.db` 而漏掉 `-wal`，会丢失最近交易数据（signals 509 行、seals 1141 行、summaries 71 行都在其中）。
- 建议：核查备份策略是否包含 WAL；在 worker 空闲时段（如 23:00）执行 `PRAGMA wal_checkpoint(TRUNCATE)` 并纳入定时任务。本次只读检查**没有执行 checkpoint**（写操作需用户确认）。

#### P2-3 日志噪音
- 近 7 天 worker 有 **11200 行** `DEBUG | Idempotent check failed for XXX`；journald 累计 471.6 MB。
- 建议：把该 DEBUG 降级为 TRACE 或仅在命中时打一条汇总（每轮一次），预计日志量可降一个数量级。不改任何业务行为。

#### P2-4 所有新开关靠代码默认值，`.env` 不显式
- 逐一核对：`EM_GLOBAL_THROTTLE` / `INTRADAY_KLINE_CORRECTION` / `KLINE_CROSS_CHECK` / `KLINE_EOD_SEAL` / `KLINE_DAY_BOUNDARY_GUARD` / `SOURCE_TIMEOUT_SUPPRESSION` / `AI_PARTIAL_NOTIFY` / `API_AUTH_TOKEN` / `KLINE_REJECT_STALE_FRAME` / `DAILY_REPORT_DISCIPLINE_DIMENSION` —— **均不在 .env**。
- 默认值经代码核对符合预期（前 7 项 True，`API_AUTH_TOKEN` 空，`KLINE_REJECT_STALE_FRAME=False`，`DAILY_REPORT_DISCIPLINE_DIMENSION=False`）；但运维不可见、改默认值会静默改变线上行为。
- 建议：把关键开关显式写进 `.env`（含 `API_AUTH_TOKEN` 的占位注释），使「线上配置 = 可读配置」。**注意**：这是配置暴露面调整，配合 P0-1 一起做。

#### P2-5 版本记录不可追踪
- `/root/ecs_version_*.txt` 三次记录全为 `no-git`；ECS 目录不是 git 仓库，无法从文件确认精确 commit。
- 11-14 06:46 三服务有一次 stop/start（journal 有记录），但代码 mtime 仍是 11-07 → 只是重启，无代码漂移（已核实，无需处理）。
- 建议：部署脚本把本地 `git rev-parse HEAD` 写进版本记录文件（不改部署逻辑本身）。
