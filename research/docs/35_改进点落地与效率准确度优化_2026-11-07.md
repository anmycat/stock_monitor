## 3. 效率优化：失败路径是最大瓶颈

### 3.1 问题

`docs/34` §3.4 记录：东财 `fflow` 在本地代理下每次失败要 ~10s × 3 次重试，导致 3483 次扫描跑不完，D41 回归被迫用 `/tmp/sm_reg_wrapper.py` 打 monkey patch。生产侧同理——单个不可达源（TDX 网关、东财风控）会把全市场扫描拖垮。

### 3.2 做法

| 位置 | 改动 | 效果 |
|---|---|---|
| `data/source_manager.py` | `classify_failure()` 用异常类名 + 消息特征识别网络类失败；命中即 `break` 跳出重试循环 | 单次失败从 ~30s 降到 ~10s，且立即让下一个源接手 |
| 同上 | 连续 2 次同类超时 → `suppress_until = now + 20s`，窗口内 `is_available()` 直接跳过该源 | 故障期不再每票重复撞墙；其它源照常 fallback |
| 同上 | 抑制/冷却/熔断状态经 `attach_cache()` 写 Redis（节流 5s），重启恢复 | 重启后不再「重新撞一遍墙」 |
| `services/signals/signal_generator.py` | `set_capital_flow_provider()` 正式注入点 | 回归脚本可摆脱 `/tmp` wrapper 的猴子补丁 |
| `UX/static/index.html` | `fetchAPI` 同端点 in-flight Promise 复用 | 多窗口/重复刷新不再发重复 HTTP |
| `data/repositories/market_data.py` | `invalidate_daily_cache(code, session=None)` 二次精确过滤 | 修补历史数据后无需等 TTL 3600，且不会误删其它标的缓存 |

**可回退**：`SOURCE_TIMEOUT_SUPPRESSION=False` 即回到「每次重试」旧口径；`SOURCE_TIMEOUT_SUPPRESS_SECONDS` / `SOURCE_TIMEOUT_SUPPRESS_STREAK` 可调。

## 4. 准确度优化：从「末根」到「整帧」，从「后端可见」到「用户可见」

### 4.1 整帧校验（I-04）

DSA #2389 的关键洞察是「因子消费整份序列，混入一个节假日 bar 即整帧不可信」，而 D66 的 `assess()` 只判末根。新增 `validate_frame()` 检查：

- 每根日期可解析、**严格单调**、无重复
- 每根都是**交易日**（带 `lru_cache`，日历不可用时保守放行，不误报历史回测数据）
- 无未来 bar（`> session`）
- OHLC 正数且 `low ≤ open/close ≤ high`

结论写 `df.attrs['kline_frame_health']`，**一列都不改**——MA/RSI/MACD/回测读列，天然零影响。异常状态写 `kline_frame_issue:{session}:{code}`（TTL 7 天），只有显式 `clear_issue()` 才清除，重启不绕过。

**拒绝层** `KLINE_REJECT_STALE_FRAME` 默认 **False**：开启后「整帧异常 + 非当日」的数据不再出厂，这**会改变信号**，按项目纪律必须先做 D41 双跑 + 半年窗口复验 + 用户裁定。本轮只交付能力，不启用。

### 4.2 血缘透出（I-06 / I-09）

D66 做好的 7 个 `kline_*` 标签此前**完全止步后端**，用户看不到。本轮把它们收敛成 `kline_provenance.evidence()` 只读证据块，逐级透出：

```
日K df.attrs → Signal 5 字段 → signal_to_api_dict / SignalResponse → 信号卡
                                    → DailyReportBuilder._build_evidence() → 日报首区
```

信号卡现在显示「数据截至 2026-11-06 · 隔夜 T-1 · 源 sina · 复核 confirmed_lagging」，以及 D64 的现价/基准偏离提示。日报首区附「门控状态/综合分/仓位建议由代码计算」的来源声明。**这些字段不参与任何评分、风控、Kelly 或通知决策**。

### 4.3 AI 失败时的诚实降级（I-11）

原 `_generate_local()` 会返回一份结构完整、看起来像正常总结的模板，用户无从分辨模型是否参与。现在返回 `partial=True / degraded=True / missing_sections=['ai_narrative']`，并在 `full_text` 追加显式说明「仅为客观数据与规则结论，未包含模型研判」。

## 5. I-03：ECS 实测结论是「终止」，不是「换库」

按 `docs/34` I-03 的裁定，第一步必须在 ECS 跑已有的 `research/scripts/probe_tdx_nodes.py --emit-config`。11-07 在 ECS（`Python 3.14.4`、pytdx 可用）实跑：

```
候选节点 74 个（项目现有 + mootdx 38）
① TCP 可达 29/74（6.1s）
② 最终可用 0/29（0.6s）
=== 建议 TDX_SERVERS（按实测可用）===   （空）
```

29 个 TCP 可达节点**全部**协议探活失败（`quotes 无有效价格`，个别 `ConnectionResetError`）。

**结论修正**：这**不是** ECS 出口封 7709（网络层是通的），而是上游公共 TDX 行情服务器整体停供——与 D53 记录「TDX 公共节点已停供行情（协议级探测 quotes/bars 全空）」一致，现在在 ECS 得到独立实证。因此 eltdx 的「主站测速 / 连接池 / 心跳 / 连接代次隔离」**全部无法解决该问题**（测速只测 TCP 延迟，而 TCP 本来就通）。按 `docs/34` 的裁定：**I-03 到此为止，不引入 eltdx、不改 `TDX_SERVERS`、不整体换库**。能力中心的 `/api/data-capability` 会持续暴露 tdx 的熔断/降级状态供运维观察。
