# 阿里云 ECS 部署与信号推送方案

> 版本：v1.0 · 2026-10-14
> 上游依赖：`rules/methodology_rules.json` v1.1（13 条规则 DSL + Kelly 参数）、docs/09（双池回测验证）、docs/11（三条新规则验证结论）
> 本文回答两个部署约束带来的全部工程问题：**(1) 系统运行在阿里云 ECS；(2) 不接入券商 app，只通过行情接口发现判断并推送消息，人工执行**

---

## 1. 两个约束带来的架构变化

### 1.1 约束一：ECS 运行 → 本地能力全部失效

| 本地依赖 | ECS 上的状态 | 替代方案 |
|---|---|---|
| neodata MCP 行情/基本面工具 | **不可用**（MCP 是本地 agent 通道） | 直连东方财富 push2 HTTP 接口（§4） |
| CDP 浏览器抓取（雪球/知乎/快手） | 不可用（无 GUI、无登录态） | 本系统不需要，规则引擎只吃日K |
| 本地 JSON 数据文件 | 需要持久化 | SQLite 单文件库 + 每日 OSS 备份 |
| 手动运行脚本 | 需要自动化 | cron 定时 + systemd 守护 |
|  proxies/本地代理 | 不可用 | ECS 公网直连（地域选对，见 §3） |

### 1.2 约束二：无券商接入 → 系统边界重新定义

系统职责收缩为四件事：**发现（数据）→ 判断（规则）→ 表达（信号卡片）→ 触达（推送）**。下单、成交、持仓由人在手机端完成。

这带来一个关键设计：**没有成交回报的情况下，系统必须自己维护"模拟持仓"来持续给出持有/退出建议**。闭环设计见 §7。

---

## 2. 总体架构

```
┌─ 阿里云 ECS（2C2G，东八区）──────────────────────────────────┐
│ cron 调度                                                     │
│   15:05 收盘计算 → 09:25 执行提醒 → 15:30 落库+备份            │
│         ↓                                                     │
│ 行情适配层（东财 push2 主源 / 新浪·腾讯备源 / SQLite 兜底）     │
│         ↓                                                     │
│ 规则引擎（methodology_rules.json 13 条 DSL，指标当日自算）      │
│         ↓                                                     │
│ Kelly 仓位 + 风控闸门（半凯利 25% 上限 / 连亏保护 / 回撤线）    │
│         ↓                                                     │
│ Signal 契约 + 持仓跟踪器（入场区间/止损/目标/仓位%）            │
│         ↓                                                     │
│ 推送队列（幂等去重 · 失败重试 · 多渠道）                        │
└───────────────────────────────────────────────────────────────┘
        ↓ 钉钉机器人（主）/ 企业微信（备）/ 邮件（兜底）
   用户手机 → 手动下单 →（可选）回报成交价 → 回写持仓
```

**设计原则**：每一层可独立测试；规则引擎与数据源解耦（换数据源不动规则）；推送层与信号层解耦（加渠道不动信号）。

## 3. ECS 选型与成本

### 3.1 两个方案对比

| 维度 | 方案 A：函数计算 FC | 方案 B：ECS 常驻 |
|---|---|---|
| 适配场景 | 每日 3 次定时触发，每次跑 2-5 分钟 | 需要长驻留进程、分钟级盘中预警 |
| 运维 | 零运维，无系统补丁烦恼 | 需 systemd 守护、安全更新 |
| 成本 | 日跑 ~10 分钟，**在免费额度内，约 ¥0/年** | 共享型 s6 / 突发性能 t6，2C2G/40G ESSD，**约 ¥600-900/年** |
| 数据持久化 | NAS 或 OSS | 本地盘 + OSS 备份 |
| 限制 | 单次执行有超时（可配 10 分钟）；冷启动 | 无 |

**建议**：Phase 1 用 **方案 A（FC 定时触发器）**——本系统是纯定时批处理（收盘后算一次信号），没有长连接需求，FC 最省心且几乎免费。当后续要做分钟级盘中预警（§10 Phase 3）再迁 ECS。

### 3.2 关键配置项

- **地域：华东 1（杭州）或华北 2（北京）**。不要选香港/海外地域——东方财富对海外 IP 有风控和限流，且延迟高
- **时区：必须 `timedatectl set-timezone Asia/Shanghai`**（ECS 默认 UTC，cron 会整体偏移 8 小时，这是最常见的坑）
- **安全组：只开必要出网**（HTTPS 443 出方向全开即可，无需任何入方向规则）
- **存储：SQLite 单文件 + 每日 tar.gz 传 OSS**（标准存储，几十 MB ≈ ¥1/年）。OSS bucket 设私有，用 RAM 子账号 + STS 临时凭证访问

## 4. 数据源适配层（核心工程）

neodata 在 ECS 上不可用，必须自建行情通道。**所有规则与回测均基于不复权日K，数据源必须保持 `fqt=0` 口径**，否则信号与验证结论全部错位。

### 4.1 主源：东方财富 push2

```
GET https://push2.eastmoney.com/api/qt/stock/kline/get
  ?secid=0.000011          # 0.=深市 1.=沪市（688 也用 1.）
  &fields1=f1,f2,f3,f4,f5,f6
  &fields2=f51,f52,f53,f54,f55,f56,f57,f58,f59,f60,f61
  &klt=101                 # 101=日K
  &fqt=0                   # 0=不复权（与全部回测口径一致）
  &end=20500101&lmt=120    # 拉足够算 MA60/RSI/KDJ 的历史
```

返回 `data.klines` 为字符串数组，每行：
`日期,开盘,收盘,最高,最低,成交量(手),成交额,振幅%,涨跌幅%,涨跌额,换手率%`

**换手率字段（f61）东财直给**，不需要自算——但备源没有，见 4.3。

### 4.2 备源

- **新浪**：`https://money.finance.sina.com.cn/quotes_service/api/json_v2.php/CN_MarketData.getKLineData?symbol=sz000011&scale=240&ma=no&datalen=120`（字段：day,open,high,low,close,volume——**无换手率/振幅，需用静态流通股本表自算**）
- **腾讯**：`https://web.ifzq.gtimg.cn/appstock/app/fqkline/get?param=sz000011,day,,,120,qfq`（结构带 qfq/hqfq 分级，取 day 节点）

### 4.3 failover 与兜底策略

```
拉取顺序：东财 → （失败/超时3s）→ 新浪 → （失败）→ 腾讯 → （全失败）→ SQLite 本地缓存
```

- **缓存兜底**：即使全源失败，用本地最近数据算信号，但推送卡片必须标注 `⚠ 数据陈旧至 YYYY-MM-DD`
- **连续失败告警**：主备源全挂连续 2 个交易日 → 推送告警消息（防止静默失效）
- **限流**：全池 27 只逐个拉取，间隔 300-500ms；单只失败指数退避重试 2 次
- **静态股本表**：备源自算换手率需要流通股本，维护一份 `config/float_shares.json`，每周用东财接口刷新一次

### 4.4 为什么不用 akshare

akshare 封装了上述接口，但上游接口一变就整库崩，且依赖重（pandas/numpy 在 FC 上拖慢冷启动）。**直接 requests 打接口 + 自己解析**，与项目"指标自算、不信任外部快照"的一贯纪律一致（参考 neodata 估值快照陈旧 bug 的教训，docs/11 §7）。

## 5. 规则引擎对接

### 5.1 引擎输入输出契约

```
输入：日K序列（不复权）+ 当日已知指标（MA5/MA20/RSI6/KDJ_J 自算）+ 上证指数序列 + PE/ROE 快照
输出：Signal 列表（§6 契约）
配置：rules/methodology_rules.json v1.1（13 条规则 + kelly 参数，原样加载，不硬编码）
```

### 5.2 采纳配置（来自 docs/11 验证结论，必须按此配置运行）

| 规则 | 运行方式 | 依据 |
|---|---|---|
| R11 市赚率 | **选股层负面清单**（PR>0.8、亏损股、ROE≤0 不进池），不做信号闸门 | 信号闸门证伪：过滤后仅剩 6 笔；但负面清单对博主 43 笔买入 100% 命中 |
| R12 预期差 | **默认开启**过滤（信号日前 5 日 >15% 或 10 日 >25% 放弃） | 博主"透支后追入"7 笔胜率 0%；注意动量规则自身涨幅不误杀（阈值已按射程校准） |
| R13 牛熊 | **改造为变体：指数 bias20 ≤ -2% 时禁止 R05 低吸** | 原设计"熊市禁开仓"证伪（+25.47%→-88.99%）；变体使累计 +25.47%→+63.64% |
| R01-R06 交易规则 | 正常运行，资金四分类（SC/HC/YZ/DR）先行，射程匹配后执行 | docs/09 双池验证 |
| R10 连亏保护 | 全期有效（连亏 3 笔或回撤 -10% 停止开新仓） | Kelly 配套 |

### 5.3 当日可知纪律的工程实现

- 所有指标（MA/RSI/KDJ）由引擎从日K**自算**，不依赖外部指标接口
- 信号生成固定在 **15:05**（收盘后），成交假设为 T+1 开盘价——与回测口径完全一致
- **盘中不生成信号**（Phase 3 的分钟级预警只做"价格触及已生成信号的入场区间"提醒，不产生新信号，不破坏纪律）

## 6. Signal 契约与推送卡片

### 6.1 Signal 字段定义

```json
{
  "signal_id": "S-20261014-300308-B",
  "code": "300308.SZ", "name": "中际旭创",
  "direction": "long", "rule": "R01", "rule_name": "动量突破买入",
  "rating": "B", "confidence": "high",
  "capital_tag": "HC-01", "regime": "neutral",
  "signal_date": "2026-10-14",
  "entry_range": [10.20, 10.50],
  "stop_loss": 9.80, "take_profit": 11.50,
  "position_pct": 0.15,
  "reason": "连涨2日+量比1.8+突破20日高点",
  "executable": true,
  "exec_note": ""
}
```

### 6.2 推送卡片（钉钉 markdown，可直接执行）

```
【买入信号】中际旭创 300308 · 评级B
━━━━━━━━━━━━━━━━
方向：买入（R01 动量突破 · 起爆资金跟随）
入场区间：10.20 – 10.50（T+1 开盘价在区间内可市价买入）
止损：9.80（-4.5%）   目标：11.50（+11%）
建议仓位：15%（Kelly 半仓 × 相关性折扣，账户上限 25%）
置信度：高
━━━━━━━━━━━━━━━━
信号逻辑：连涨2日 + 量比1.8 + 突破20日高点；指数 bias20=-1.2%（非急跌日，R05 类信号可用）
⚠ 个人研究工具输出，非投资建议
```

### 6.3 不可执行标注（T+1 开盘时由系统自动判定）

| 情形 | 判定 | 推送措辞 |
|---|---|---|
| 开盘价 ≥ 涨停价 | 一字涨停，无法买入 | `开盘涨停，放弃或排队，勿市价追` |
| 开盘价 ≤ 跌停价 | 信号作废 | `开盘跌停，信号作废` |
| 开盘价在入场区间 | 可执行 | `开盘 XX.XX，区间内，可执行` |
| 开盘价 > 区间上限 3% | 透支，放弃 | `开盘跳空超上限，放弃` |
| 停牌 | 跳过 | `停牌，跳过` |
| 前收突变 >15% 且非涨跌停 | 疑似除权 | `⚠ 疑似除权跳空，信号价格失真，人工确认` |

涨跌停价计算：`昨收 × (1 ± limit%)`，limit 按板块取：主板 10%、ST 5%、双创（688/300）20%。**代码板块判定用静态映射表**，不实时查。

## 7. 无券商接入的执行闭环（本方案核心）

四段闭环，人工执行被显式建模进系统状态机：

```
① T日 15:05  收盘计算 → 生成信号卡片 → 推送「预信号」
② T+1 09:25  集合竞价后 → 开盘价校验 → 推送「执行确认」
③ T+1 盘中    用户手动下单 → 可选回报 → 系统记录成交
④ 持仓期      每日推送「持有 / 加 / 减 / 清」建议（R06 倒T、DR-01 派发、R08 游资反向）
```

### 7.1 成交回报协议（可选但强烈建议）

用户在对对谈/群里回复简单文本，系统解析回写：

```
B 300308 10.35 5000      # 方向 代码 成交价 股数
S 300308 11.80 5000      # 卖出
```

- 解析容错：全角/半角、空格、逗号分隔都接受
- **未回报的处理**：按信号价（区间中值）记"模拟成交"，持仓跟踪继续，卡片标注 `模拟持仓`
- 回报纠正：再次回复同方向同代码即覆盖上一次

### 7.2 持仓跟踪器状态机

```
PENDING(预信号已推) → OPEN(已成交/模拟成交) → CLOSED(卖出/止损/目标)
                        ↓
                  每日重算：DR-01 派发信号→建议减仓；R06 倒T→做T建议；
                  R10 连亏保护→全局冻结开新仓
```

- 每个持仓每日推送一次状态卡（浮盈亏按当日收盘价，不复权口径）
- 止损/目标触发由系统算（日K口径：收盘价破止损线即提示，非盘中价——与纪律一致）
- **账户级风控**：连亏 3 笔或组合回撤 -10% → 推送 `风控冻结：停止开新仓 N 日`

### 7.3 为什么这样设计

没有券商 API 时，最大的风险不是"漏信号"，而是**信号推送后系统就失联了**——用户买没买、什么价买的、现在该不该卖，系统一概不知，方法论的全部价值（持有/退出/风控）就丢了。回报协议用最低成本（一条文本消息）把人工执行接回系统状态机，是整套方案里性价比最高的设计。

## 8. 调度设计

```cron
# crontab -e（ECS/FC 均适用，时区 Asia/Shanghai）
30 9  * * 1-5   python3 main.py open_check    # 竞价后开盘价校验 + 执行确认推送
5  15 * * 1-5   python3 main.py signal        # 收盘计算 → 信号生成 → 推送
30 15 * * 1-5   python3 main.py persist       # 数据落库 + OSS 备份 + 健康检查
0  16 * * 0     python3 main.py weekly        # 周报：本周信号胜率/持仓盈亏/风控状态
```

**工程要点**：

1. **交易日判断**：主源返回当日有日K才是交易日；另维护 `config/holidays.json`（每年初更新）兜底。非交易日 cron 照跑但直接退出（幂等）
2. **幂等**：`signals` 表以 `(signal_date, code, rule)` 建唯一索引；同日重跑只更新不重复推送
3. **进程守护**（ECS 方案）：systemd unit + `Restart=always`；FC 方案由平台保证
4. **失败告警**：任何任务异常 → 邮件兜底渠道推送（防止钉钉挂了连告警都收不到）
5. **日志**：stdout 进 journald；关键事件（信号生成、成交回报、推送成败）写 SQLite `events` 表，周报直接查

## 9. 工程坑位清单（从本项目踩坑史迁移）

| # | 坑 | 规避 |
|---|---|---|
| 1 | ECS 默认 UTC 时区，cron 整体偏移 8 小时 | `timedatectl set-timezone Asia/Shanghai`，部署第一步 |
| 2 | 复权口径混用导致信号价与用户盘口不一致 | 全链路 `fqt=0` 不复权，信号卡直接用此价格 |
| 3 | 除权日不复权跳空，信号价格失真 | 前收突变 >15% 且非涨跌停 → 标注除权，人工确认 |
| 4 | 一字涨停/跌停无法成交 | T+1 开盘价 vs 涨跌停价预检（§6.3） |
| 5 | 东财 IP 限流 | 全池拉取间隔 300-500ms + 指数退避；选国内地域 |
| 6 | 备源无换手率字段 | 静态流通股本表自算，每周刷新 |
| 7 | webhook token 硬编码进 git 泄露 | 环境变量 / 阿里云 KMS；`.env` 权限 600；`.gitignore` 排除 |
| 8 | 数据静默失效（接口改了不报错） | 连续失败告警 + 数据陈旧标注 + 周健康检查 |
| 9 | Kelly 单位混用（小数/百分数）——docs/11 实际踩过 | 全链路百分数，入库前断言 0 < position ≤ 25 |
| 10 | 板块涨跌幅限制（ST/双创）判定错 | 静态板块映射表 + 每日与东财静态信息接口对账 |

## 10. 安全与合规

1. **免责声明**：每条推送 footer 固定带 `⚠ 个人研究工具输出，非投资建议`；README 显著位置声明
2. **使用边界**：个人自用工具，不公开传播信号、不代客理财、不建收费群——越过任何一条都涉及非法荐股/非法经营
3. **密钥管理**：webhook token、OSS AK 走环境变量或 KMS；ECS 用 RAM 子账号最小权限（只写自己的 OSS bucket）
4. **数据合规**：行情数据仅个人学习研究使用，不转售不公开再分发

## 11. 实施路线图

### Phase 1 · MVP（约 1 天）

FC 定时触发器 + 东财单源 + SQLite + 规则引擎（v1.1 采纳配置）+ 钉钉推送 + 信号卡。**验收标准：连续 5 个交易日每天 15:05 准时收到信号卡，无重复无遗漏。**

### Phase 2 · 完整闭环（约 1 周）

多源 failover + 开盘执行确认 + 回报协议 + 持仓跟踪器 + 账户级风控 + 邮件兜底 + OSS 备份 + 周报。

### Phase 3 · 增强（持续）

- 分钟级盘中预警（触及入场区间提醒，不产生新信号）
- 回测池扩容 100+ 只/12 个月后复测 R11 正面结论（docs/11 局限）
- 信号胜率统计看板（events 表聚合）
- 多账号/家庭共享推送（仅个人使用前提下）
