### 3.1 DSA #2389：日线缓存新鲜度（A 级，最高相关）

`77e419281d`（10-05）改动 `src/services/screening/daily.py +147/-22`，新增 `tests/test_screening_daily_freshness.py` **734 行 / 30 个测试**。直读当前 `main` 的 `daily.py` 后，比 `docs/32` §2.2 多出四点：

1. **校验的是整帧，不只是末根**（`_latest_daily_bar_date()`，L~470）：
   ```python
   # A valid latest bar cannot make an earlier holiday/weekend close
   # usable: factors consume the entire frame, including those rows.
   for bar_date in dates.dropna().unique():
       if not is_market_open(market, pd.Timestamp(bar_date).date()):
           return pd.NaT
   ```
   只要历史帧里混入一个周末/节假日 bar，整份数据判为无效。本项目 D66 `assess()` **只判末根**。
2. **取数时间二次校验**：`daily_history_is_stale(..., fetched_at=...)` 用取数时刻重建市场阶段，判断 `acquired.effective_daily_bar_date < current.effective_daily_bar_date`——即「缓存写入时是新的，但现在已跨日」也要判陈旧。
3. **结构化健康元数据**（`daily_source_health` 19 处 / `daily_source_order` 20 处）：stale 候选保留 `daily_source_order_notes`、`source_errors`、`daily_source_health`；连**抛异常时**也把同一份诊断挂在 `error.daily_metadata` 上，让上层仍能评分。本项目 `source_manager` 无等价物。
4. **30 个测试边界**覆盖：非交易日 bar 继续 fallback、缓存需 session 新鲜度而不止 TTL、收盘切换刷新未完成 bar、注入 provider 不能绕过新鲜度校验、所有源都 stale 时保留最不陈旧的一份、日历不可用时退回 TTL 且保留显式 stale 标记等。

**一处代码摘引更正（结论方向不变）**：`docs/32` §2.2 第 6 点把取数循环摘引为 `` `if is_stale: ... continue` ``，源码实际是 `break`，且位于 `for attempt in range(attempts)` **内层重试循环**；外层 `for current in sources` 仍继续下一个源，所以「继续找下一个源」的结论成立，但代码摘引不准确，已在 `docs/32` 就地更正。准确表述应为「**中止该源的剩余重试 → 记为 stale 候选 → 继续下一个源 → 全部 stale 时返回最不陈旧的一份并带标**」。D66 目前是「独立第二源针对性复核」，两者不同构但互补。

## 4. 新发现的 6 个项目

### 4.1 `electkismet/eltdx` —— 直击「TDX 池不可达」（C 级能力 + B 级发版）

687★ / 267 fork / Python / 创建 2026-02-26 / push & release 均 11-06。README 自述「7709 协议核心由 Rust 实现，支持 MCP 与 HTTP 网关」，能力表明确列出**主站测速、Rust 连接池、心跳、pin、push、缓存和 diagnostics**（L81）。相关段落：

- L306-311：不传 host 时用默认候选主站；`probe_hosts=False` 默认关闭自动测速，显式 `probe_hosts=True` 或 `refresh_server_ranking()` 触发；**测速只做 TCP connect 延迟**，排名原子写入 `tdx_server_ranking.json`，下次启动先用上次排名再刷新；明确声明「不等于完整业务请求质量测试」。
- L336-354：连接池参数 `max_connections_per_host`（单台活动连接硬上限，重连也遵守）、`connect_concurrency_per_host`、`heartbeat_interval=30.0`（后台心跳保活）。
- L361-375：`client.transport.diagnostics` 可查真实线程数、已连主站、内存占用；「某条连接超时或返回异常时，**只废弃当前 Slot 的连接代次，避免迟到响应污染后续请求**」。
- Release：v3.3.5(11-06) 修 EX 会话初始化与 MAC-EX 主机探活、改善主站查询超时；v3.3.3(11-06) 订阅每 7 秒游标续期 + 多连接批量订阅；v3.3.2(10-30) 批量查询新增 `on_missing="raise"/"skip"`，默认严格报错并用 `MissingCodesError.missing_codes` 列出缺失代码。

**与本项目已有工具的互证（重要）**：`research/scripts/probe_tdx_nodes.py`（190 行，D53 遗留）**已实现同一思路的雏形**——候选 = 项目 `TDX_SERVERS` + mootdx 38 节点，两级探测（TCP connect 2s 快速筛 → pytdx 连接并取 1 根日K 验证），`--emit-config` 直接产出可粘贴配置，本机实测 14 个节点存活；脚本注释明确「**TCP 通 ≠ TDX 协议可用：部分节点会接受连接但不响应协议**」以及「在**生产 ECS 上跑**才有意义（出口 IP/网络路径与本机不同）」。eltdx README 也独立声明「测速只做 TCP connect 延迟，**不等于完整业务请求质量测试**」——两边独立得出同一结论。因此 I-03 的真实缺口**不是没有探测工具**，而是：① 未在 ECS 上执行并把结果固化进生产配置；② 无排名持久化 / 心跳 / 连接代次隔离。

**重要边界**：以上 eltdx 能力均为 README/Release 自述（C/B 级），**本轮未在 ECS 上实测其主站可达性**。本项目 ECS 日志是 `TdxSource: 服务器池全部不可用 / No route to host`，若 ECS 出口整体禁止 7709 端口，测速与连接池也救不了。因此 I-03 的第一步是**在 ECS 上跑已有的 `probe_tdx_nodes.py`**，而不是新写工具或直接换库。README 还提到其迭代项目 `AxData`（插件化接入交易所/巨潮/腾讯/新浪/东财等），本轮仅登记、未展开。

### P1 — 数据质量与可靠性

#### I-03 TDX 链路：主站测速 / 连接池 / 心跳 / 连接代次隔离
- **证据**：eltdx README L286-375 + v3.3.2/3.3.3/3.3.5（C/B 级）
- **现状**：固定 117.34.114.x 网关、ECS `服务器池全部不可用`；`manifest d53.remaining` 记 mootdx bestip 探测待接入。**但仓库已有 `research/scripts/probe_tdx_nodes.py`（190 行）**：候选 = 项目 `TDX_SERVERS` + mootdx 38 节点，TCP 快速筛 + pytdx 实取数两级验证，`--emit-config` 产出可粘贴配置，本机实测 14 节点存活，注释明确「ECS 上跑才有意义」——**工具不缺，缺的是 ECS 实测与配置闭环**
