- **关键提交**：`77e419281d`（2026-10-05）`fix: 修复选股日线缓存新鲜度并保留策略元数据 (#2389)`，改动 `src/services/screening/daily.py +147/-22`、新增 `tests/test_screening_daily_freshness.py`（**734 行**）
- 另有 `ebab2ba9f5`（10-04）`feat: add data capability center (#2304)`——数据源能力元数据面板

### 2.2 它的做法（raw 源码直读）

`daily_history_is_stale()` 的核心判据（`src/services/screening/daily.py` 515-548 行）：

1. 用 **市场阶段上下文**（`MarketPhase` + `effective_daily_bar_date` + `session_date`）而非自然日判断
2. 校验 `effective_daily_bar_date <= latest_bar_date <= session_date` 这个**闭区间**，越界即 stale
3. 非交易时段/盘前要求末根日期**恰好等于** effective date
4. 保留 provider 的 session 日期，不把 date-only bar 经 UTC 转换（避免跨时区错位）
5. 陈旧标记写 `hist.attrs["daily_stale"] = True`；所有源都陈旧时仍返回"最不陈旧"的一份供降级使用，但**明确带标**
6. 取数循环里：`if is_stale: ... continue`——**遇到陈旧源继续往下找下一个源**，而不是拿第一个非空结果就返回

### 2.3 与 D66 的对照

| 维度 | DSA (#2389) | 本项目 D66 | 评价 |
|---|---|---|---|
| 陈旧标记载体 | `df.attrs['daily_stale']` | `df.attrs['kline_as_of'/'kline_sealed'/...]` | 同构，D66 字段更丰富 |
| 交易日锚点 | `effective_daily_bar_date` / `session_date` | `expected_session()` / `is_adjacent_session()` | 同构，D66 用静态休市日表 |
| 跨日缓存 | TTL + 新鲜度双重校验 | **缓存 key 带交易日** + 隔夜 stale 快照作废 | D66 更彻底（key 层面隔离） |
| 陈旧源处理 | fall through 到下一个源 | **独立第二源针对性复核** | D66 多了交叉验证，DSA 只是跳过 |
| 收盘封存 | 未见 | SQLite `daily_bar_seals` + 日期/来源/复核标签 | D66 独有（用户要求） |
| 测试规模 | 734 行单文件 | `test_daily_guard_d66.py` 21 例 + `test_log_fixes_d66.py` 9 例 | 量级不同，覆盖点对齐 |

**可借鉴且已补进 D66 的一点**：DSA 明确"所有源都陈旧时返回最不陈旧的一份、但必须带标"。D66 当前在 `assess()='stale'` 时不拒绝数据（只记日志），保持了 D41 零漂移纪律；这一点应在后续实盘取证后再决定是否收紧为"拒绝出信号"，不宜本轮直接改（会改变信号，需另跑双跑回归）。
