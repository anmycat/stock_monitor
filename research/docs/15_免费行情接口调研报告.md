# 免费实时行情接口调研报告

> 版本：v1.0 ｜ 日期：2026-10-15 ｜ 用途：为 ECS 部署的量化扫描系统选型行情数据源
> 方法：本机实时实测（延迟/成功率/批量能力）+ 全网检索（官方文档 + 技术公众号文章）+ GitHub 项目健康度核查
> 说明：所有"实测"数据均来自本次调研环境（家庭宽带，非 ECS），生产环境表现需以 ECS 实测为准

## 一、结论摘要

| 方案 | 注册 | 延迟 | 稳定性（实测） | 建议定位 |
|---|---|---|---|---|
| **腾讯 qt.gtimg.cn** | 免注册 | ~0.2s | 15/15 稳定，支持 60 只/次批量 | **主力实时源** |
| **新浪 hq.sinajs.cn** | 免注册 | ~0.2s | 15/15 稳定 | **备源 1（实时）+ 分钟K 源** |
| 东方财富 push2 | 免注册 | ~0.2s（未封时） | burst 后秒封：0/15，>65s 未恢复 | **仅限流备用**，不可依赖 |
| **Tushare Pro** | 需注册（120积分=注册100+资料20） | HTTP，秒级 | 未实测（需 token） | **日K/历史数据主力** |
| 网易/和讯 | 免注册 | — | 已失效 | 放弃 |
| stooq | 免注册 | 慢 | 格式需修正 | 备选 |
| 雅虎财经 | 免注册 | — | 429 限流 | 放弃 |

**核心建议（对应 stock_monitor 现有 SourceManager 架构）**：
1. 实时行情：腾讯为主、新浪为备（与项目现有 `_PRIORITY.realtime=[eastmoney,tencent,akshare]` 相比，**建议把东财降级**——本次实测证明其 burst 封禁风险会拖垮整条链路）
2. 日K/历史：akshare 为主（封装多源），Tushare 注册后作为补偿源
3. 分钟K：新浪/腾讯直连（腾讯需修正 URL 参数格式）
4. 无论选谁，**多源 failover + 限流 + 快照回退**是硬性要求（东财封禁实测教训）

## 二、免注册直连接口实测

### 2.1 腾讯财经 qt.gtimg.cn

- **实时快照**：`https://qt.gtimg.cn/q=sh600519,sz000001,...`
- 实测：**15/15 成功，延迟 ~0.2s**
- 批量能力：一次请求 60 只代码（约 30KB），返回完整（已验证逐条解析）
- 编码 GBK，`~` 分隔字段（项目 tencent.py 已有解析实现：parts[3]=价格、parts[32]=涨跌幅）
- 分时/分钟数据可用（~0.29s），但部分 K 线 URL 参数格式返回 param error（需对照项目内实际 URL 修正后使用）
- **结论：免注册接口中最优，延迟低+稳定+批量强**

### 2.2 新浪财经 hq.sinajs.cn

- **实时快照**：`https://hq.sinajs.cn/list=sh600519,sz000001`
- 实测：**15/15 成功，延迟 ~0.2s**，GBK 文本格式（values[3]=价格、values[32]=涨跌幅）
- **分钟K**：实测 0.36–0.71s 可用（慢但可靠，适合非盘中路径）
- **结论：最佳备源，分钟K 场景优于腾讯**

### 2.3 东方财富 push2（重要风险发现）

- **实时快照**：`https://push2.eastmoney.com/api/qt/clist/get?...pz=5000`（全市场单次拉取）
- 实测：**首轮 3 家均 200 成功**；连续 burst 后**东财全部失败（0/15）**，表现为 "Remote end closed connection without response"（TCP 层直接拒连，非 HTTP 错误码）
- 暂停 **65 秒后仍未恢复**；更换域名（push2delay / 80.push2）同样被封
- **解读**：东财对突发流量极敏感，触发的是 IP 级风控而非频次软限制。全市场扫描类系统（pz=5000 + 循环刷新）极易踩雷
- **结论**：可作为低优先级备源，但必须满足：① 严格限流（项目已有 20次/分钟）② 连续错误快速熔断（项目已有 3 次错误→300s 冷却）③ 绝不做高频重试

## 三、慢速接口与失效源（按用户要求纳入评估）

| 接口 | 状态 | 说明 |
|---|---|---|
| 网易财经 CSV | **已失效** | 接口下线，无法获取 |
| 和讯 | **已失效** | 同上 |
| stooq | 数据可得，**格式需修正** | CSV 字段布局变动，需重新适配解析；速度慢 |
| 雅虎财经 | **429 限流** | 免费额度极紧，A 股支持差 |
| 新浪分钟K | **可用（慢）** | 0.36–0.71s，适合收盘后/低频路径 |
| 腾讯分时 | **可用** | ~0.29s |

**慢速接口的合理用法**（与"允许慢速接口"对应）：分钟K/日K 等非实时路径不参与盘中决策，可用慢源 + 本地缓存（项目 DataCenter 已有 quote 60s / daily 3600s / minute 300s 分层缓存），把慢源对系统的影响降到零。

## 四、注册制 API（需注册的均已标注）

### 4.1 Tushare Pro —— 最推荐的注册制源

- **注册**：tushare.pro 手机注册，**送 100 积分**；完善个人资料再 **+20 积分 = 120 积分**
- **额度规则**：积分决定每分钟可调用频次；120 分档位**恰好覆盖日线等基础行情接口**
- **免费边界**：日K/复权/基础财务免费额度内可用；tick、分钟级、逐笔等高频/深度数据需更高积分或付费
- **未实测原因**：需要 token（注册账号后获得），本次调研未注册
- **适配建议**：注册一个账号作为 akshare 的补偿源 + 历史数据补齐源；把 token 配到 `.env` 的 `TUSHARE_TOKEN`

### 4.2 其他注册制接口

| 接口 | 注册要求 | 免费额度 | 备注 |
|---|---|---|---|
| AllTick | 注册获取 API Key | 有免费额度 | 未实测，公众号文章常见推荐 |
| 聚合数据 | 注册 | 有免费额度 | 未实测 |
| TickDB（腾讯云） | 注册 + API Key | 有免费额度 | 腾讯云生态，未实测 |

## 五、MCP 服务器生态（GitHub 健康度核查）

检索 `akshare mcp` / `tushare mcp` 按 stars 排序，均存在多个活跃项目：

| 项目 | 健康度 | 说明 |
|---|---|---|
| Nickszy/stock-mcp | 活跃 | A股 MCP，star 数较高 |
| huweihua123/stock-mcp | 活跃 | 持续维护 |
| akshare 系 MCP（多个） | 活跃 | 封装 akshare 数据能力 |
| tushare 系 MCP（多个） | 活跃 | 封装 Tushare Pro |

**选型提示**：MCP 的价值在于让 Agent 直接调数据；但对 ECS 上 7×24 运行的扫描系统，**直接 HTTP + SourceManager 容错链路比 MCP 更可控**（MCP 多一层进程间通信故障点）。建议 MCP 只用于本地调试/Agent 问答场景。

## 六、akshare 实测说明（如实记录）

- akshare 是 Python 开源库，封装东财/腾讯/新浪等多源，项目 `akshare_source.py` 已深度使用
- 本次尝试在隔离 venv 安装 akshare 做真实冒烟测试，**因本机沙箱文件系统异常（依赖包 jsonpath 的 sdist 无法解包）多次失败，最终放弃实测**
- **已知能力**（来自其文档与项目内使用）：stock_zh_a_spot_em（东财全市场快照）、fund_etf_spot_em（ETF）、zh_a_hist（日K）、zh_a_hist_min_em（分钟K）、涨跌停池、行业板块、个股资金流
- **风险提示**：akshare 的东财系接口与 push2 同源，**东财封禁时 akshare 的 spot_em 会一同失效**（多源容错命题因此更重要——腾讯/新浪直连才是最后防线）

## 七、对 stock_monitor 的直接改进建议

项目现有 `data/source.py` 优先级：
```python
_PRIORITY = {
    "realtime": ["eastmoney", "tencent", "akshare"],   # ← 建议调整
    "minute":   ["akshare", "tencent"],                 # ← 建议加 sina
    ...
}
```

基于本次实测，建议改为：
```python
_PRIORITY = {
    "realtime": ["tencent", "sina", "eastmoney", "akshare"],  # 东财降到最后
    "minute":   ["sina", "tencent", "akshare"],               # 新浪慢但稳，分钟K 最优
    "daily":    ["akshare", "eastmoney", "tencent"],
    ...
}
```
理由：① 东财 burst 封禁是实测事实，不应作为实时首选；② 腾讯 60 只/次批量对全市场扫描最省请求数；③ 新浪分钟K 实测最稳。

## 八、风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 东财 IP 级封禁（已实测发生） | 高 | 降优先级 + 快速熔断 + 绝不高频重试 |
| 腾讯/新浪未来也可能加风控 | 中 | 保留 akshare/Tushare 作为第三四层；快照陈旧回退（项目已有 24h 标记） |
| Tushare 积分不够高频接口 | 低 | 120 分先只用于日K补偿，不接入实时路径 |
| 免费接口无 SLA，随时可能变更字段 | 中 | DataValidator（项目已有 5 类校验）+ 解析失败即熔断，不静默产出错误数据 |
| ECS 出口 IP 与家庭宽带风控策略不同 | 中 | 上线后需在 ECS 复测一轮本报告全部项 |

## 附：实测环境与方法

- 环境：macOS 家庭宽带，Python 3.13，urllib + socket timeout 8s
- 实时快照：每家 15 次连续请求，记录成功率与平均延迟
- 批量：腾讯 60 只/次请求，逐条校验返回完整性
- 东财封禁：burst 后 0/15，等待 65s 复测仍失败，切换 2 个备用域名均失败
- MCP 健康度：GitHub API 查 star / pushed_at / archived
- 未实测项已如实标注：Tushare（需 token）、AllTick/聚合数据/TickDB（需注册）、akshare（沙箱安装失败）
