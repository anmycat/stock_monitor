# 07 · 执行与故障恢复

> 版本：v1.0 · 2026-10-15
> 上游依赖：02（数据源）、03（数据模型）、05（策略矩阵）、docs/12（部署方案）
> 本文定义调度、执行闭环、推送渠道、故障恢复与实施路线。**本系统纯定时批处理，无长连接——Phase 1 用函数计算 FC，分钟级需求出现后再迁 ECS。**

---

## 1. 部署形态选型

| 形态 | 适用 | 成本 | 结论 |
|---|---|---|---|
| **函数计算 FC（定时触发器）** | 日级批处理：收盘算一次信号 | 日跑 ~10 分钟在免费额度内 ≈¥0/年 | **Phase 1/2 采用** |
| ECS 2C2G 常驻 | 分钟级盘中预警、长连接 | ¥600-900/年 | Phase 3 再迁 |

- **地域**：华东/华北（海外地域访问东财有人机验证风控）
- **时区**：`Asia/Shanghai`——部署第一步 `timedatectl set-timezone Asia/Shanghai`，cron 整体偏移 8 小时是第一个坑
- **依赖**：`requests` + `pyyaml`（Phase 1 两个包，FC 冷启动 <2s）

## 2. 调度（cron，东八区）

```cron
30 9  * * 1-5   python3 main.py open_check    # 竞价后开盘价校验 + 执行确认推送
5  15 * * 1-5   python3 main.py signal        # 收盘计算 → 信号生成 → 推送
30 15 * * 1-5   python3 main.py persist       # 数据落库 + OSS 备份 + 健康检查
0  16 * * 0     python3 main.py weekly        # 周报：信号胜率/持仓盈亏/风控状态
```

**工程要点**：
1. **交易日判断**：主源返回当日有日K才是交易日；`config/holidays.json` 兜底。非交易日 cron 照跑但直接退出（幂等）
2. **幂等**：`signals` 表 `(signal_date, code, rule)` 唯一索引；同日重跑只更新不重复推送
3. **进程守护**：ECS 用 systemd unit + `Restart=always`；FC 由平台保证
4. **失败告警**：任何任务异常 → 邮件兜底渠道推送（防钉钉挂了连告警都收不到）

## 3. 执行闭环四段（人工执行被显式建模）

```
① T日 15:05  收盘计算 → 生成信号卡片 → 推送「预信号」
② T+1 09:25  集合竞价后 → 开盘价校验 → 推送「执行确认」
③ T+1 盘中    用户手动下单 → 可选回报 → 系统记录成交
④ 持仓期      每日推送「持有 / 加 / 减 / 清」建议
```

### 3.1 T+1 开盘可执行性预检

| 情形 | 判定 | 推送措辞 |
|---|---|---|
| 开盘价 ≥ 涨停价 | 一字涨停，无法买入 | `开盘涨停，放弃或排队，勿市价追` |
| 开盘价 ≤ 跌停价 | 信号作废 | `开盘跌停，信号作废` |
| 开盘价在入场区间 | 可执行 | `开盘 XX.XX，区间内，可执行` |
| 开盘价 > 区间上限 3% | 透支，放弃 | `开盘跳空超上限，放弃` |
| 停牌 | 跳过 | `停牌，跳过` |
| 前收突变 >15% 且非涨跌停 | 疑似除权 | `⚠ 疑似除权跳空，信号价格失真，人工确认` |

涨跌停价 = 昨收 ×(1±limit%)；limit 按板块：主板 10%、ST 5%、双创（688/300）20%。**代码板块判定用静态映射表**，不实时查。

### 3.2 成交回报协议

用户回复 `B 300308 10.35 5000`（方向 代码 成交价 股数），系统解析回写 positions 表。未回报按信号价记模拟成交继续跟踪——**没有回报闭环，方法论的持有/退出/风控价值全部丢失，这是无券商接入下性价比最高的设计**（03 §4）。

### 3.3 盘中不生成新信号

Phase 3 的分钟级预警只做"价格触及已生成信号的入场区间"提醒，**不产生新信号**——盘中生成信号会破坏"当日可知"纪律，使回测口径与生产口径分叉。

## 4. 推送渠道

| 渠道 | 用途 | 失败处理 |
|---|---|---|
| 钉钉（主） | 全部信号卡/执行确认/持仓日报/周报 | 重试 3 次 → 转邮件 |
| 邮件（兜底） | 告警与钉钉失败时 | — |
| 企业微信（可选） | 替代钉钉 | 同上 |

**webhook token 走环境变量/KMS**，`.env` 权限 600、`.gitignore` 排除——token 硬编码进 git 泄露是本类项目最常见事故。

推送卡片 footer 固定：`⚠ 个人研究工具输出，非投资建议`。

## 5. 故障恢复矩阵

| 故障 | 检测 | 恢复动作 | 用户可见 |
|---|---|---|---|
| 主数据源挂 | 超时 3s/解析失败 | 自动切新浪→腾讯→SQLite 缓存 | 信号卡标 `⚠ 数据陈旧至 X 日` |
| 主备源全挂 ≥2 日 | persist 任务健康检查 | 推送告警邮件 | `数据中断告警` |
| 单只票拉取失败 | 缺口表 | 指数退避重试 2 次；仍失败该只该日不进信号，周报复盘 | 该只当日无信号（不静默） |
| 规则引擎异常 | main.py 非零退出 | 邮件告警 + 当日不推送（宁缺毋滥） | `引擎异常，今日无信号` |
| 钉钉推送失败 | HTTP 非 200 | 重试 3 次 → 邮件兜底 | 邮件收到同样卡片 |
| 进程崩溃 | systemd Restart / FC 平台 | 自动重启；重启后幂等补跑 | 无感 |
| 数据损坏 | SQLite 完整性检查 | 从最近 OSS 备份恢复 dump | 周报标注恢复事件 |
| 误推送/重复推送 | 唯一索引 + 推送前查重 | 同日同票同规则只推一次 | 无 |

**原则：宁可当日无信号，不可推送未验证信号。** 全部降级路径都在卡片上显式标注，不允许静默失效。

## 6. 健康检查（每日 persist 时执行）

```python
checks = [
  今日是否交易日（主源有日K or holidays.json）,
  27 只票日K是否全部落库（缺口=0）,
  指数数据是否落库（R13 依赖）,
  信号生成数 vs 昨日（突降 >80% → warn）,
  SQLite 完整性（PRAGMA integrity_check）,
  OSS 备份是否成功,
  磁盘剩余（>1GB）,
]
```

任一 fail → 邮件告警；全部 pass → 静默。

## 7. 备份与容灾

| 对象 | 频率 | 位置 |
|---|---|---|
| stock.db dump | 每日 15:30 | OSS bucket（RAM 子账号只写权限） |
| rules/ 快照 | 每次 signal 前 | SQLite `config_snapshot` 表（含规则库 hash） |
| 配置（config.yaml） | 变更时 | git 私有库（密钥除外） |

**规则库改了但信号为什么变？** `config_snapshot` 记录每次信号生成时的规则版本与 hash——复盘时唯一答案。

## 8. 实施路线图

### Phase 1 · MVP（约 1 天）

FC 定时 + 东财单源 + SQLite + 规则引擎（v1.3 采纳配置）+ 钉钉推送 + 信号卡。
**验收：连续 5 个交易日每天 15:05 准时收到信号卡，无重复无遗漏。**

### Phase 2 · 完整闭环（约 1 周）

多源 failover + 开盘执行确认 + 回报协议 + 持仓跟踪器 + 账户级风控 + 邮件兜底 + OSS 备份 + 周报。
**验收：模拟持仓盈亏与回测口径一致（同一信号同价成交，偏差 <0.5pp）。**

### Phase 3 · 增强（持续）

- 分钟级盘中预警（触及入场区间提醒，不产生新信号）
- 回测池扩容 100+ 只/12 个月后复测 R11 正面结论与 bull regime 结论
- 信号胜率统计看板（events 表聚合）
- 交易成本建模（做T类规则优先）
